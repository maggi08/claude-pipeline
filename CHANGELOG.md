# Changelog

Плагин `stage-pipeline`. Версия — в `plugins/stage-pipeline/.claude-plugin/plugin.json`, даты — по коммитам.
Записывается то, что меняется для человека, который гоняет пайплайн, а не список тронутых файлов.

Обновление: `claude plugin update stage-pipeline` + перезапуск Claude Code.

## 0.11.0 — 2026-09-24

Ревизия 0.9–0.10 на живых задачах: хуки и скрипты состояния прогнаны по десяти репо и 90 STAGES.md.
Выяснилось, что они писались под «правильный» STAGES.md, а живые файлы устроены иначе: в трёх репо хуки
молчали, в одном блокировали все коммиты из-за брошенной задачи, а параллельные задачи мешали друг другу.
Отсюда правило релиза: плагин читает конфиги и STAGES.md такими, какие они есть, и смотрит только на задачу
текущей ветки. И Context7 из плагина убран: API библиотек сверяется по установленному пакету.

### ⚠ Что сделать на апгрейде

- Ничего не менять в проектах и старых задачах: формы, которые раньше ломали хуки, теперь понимаются как есть.
- Кроме force-прогонов, завершённых до 0.11: они не закрывали заголовок блока. Пока ветка такой задачи в работе,
  допиши `— завершён <дата>` в заголовок `## Force-прогон <дата>` — иначе на этой ветке агент коммитит сам.
- `CONTEXT7_API_KEY` больше не нужен — строку можно убрать из профиля шелла. Разрешение
  `mcp__plugin_stage-pipeline_context7` покажет `node "$PERMS" --check` как устаревшее, запись
  `plugin:stage-pipeline:context7` в `~/.claude/mcp-needs-auth-cache.json` безвредна.
- `/pipeline-doctor` теперь сверяет `main_branch` с тем, куда реально вливаются ветки. Если фичи идут в `dev`,
  а в конфиге `main`, whole-branch ревью и `floor-guard --base` захватят чужие смёрженные PR — поправь одну
  строку, когда в этом репо стартует следующая задача.

### Context7 убран — API библиотек по установленному пакету

Context7 из 0.8.0 требовал ключ или OAuth от каждого разработчика, без него молча выключался (Claude Code
кэширует сервер как needs-auth) — и на машине автора он так и не заработал, а пайплайн этого не заметил.
При этом он отдавал документацию «примерно этой версии», а точная версия лежит в репо.

- `docs-lookup` отвечает по установленному пакету версии из локфайла: типы (`.d.ts` — сигнатуры, опции,
  `@deprecated`; экспорта нет в типах — нет в версии), `CHANGELOG.md`/`README.md` пакета (breaking, миграции),
  исходник (поведение). Не хватило — официальная документация этой версии через WebFetch. Пакет не установлен
  и сети нет — «не сверено» в три строки, без утверждений по памяти. Офлайн, без ключа.
- `deps-audit`: deprecated и преемник — `npm view <pkg>@<версия> deprecated` и `time`, API — по типам пакета.
- `pro-review`, `/root-cause`, `stage-implement`, `/stage-kickoff` — то же правило «сверять с установленной версией,
  а не с памятью», другой источник. Из `.mcp.json`, `/pipeline-doctor`, `/pipeline-init`, ROLLOUT и README — убран;
  наружу с машины теперь уходят только `npm view` и WebFetch доков по разрешённым доменам.
- eval: `docs-lookup-version-mismatch` идёт по стабу `node_modules` (react-router-dom@6.22.3: типы и CHANGELOG
  v6), `docs-lookup-no-context7` → `docs-lookup-not-installed`; харнесс пропускает кейс, если просит MCP-сервер,
  которого нет в плагине.

### Хуки смотрят только на задачу текущей ветки

- **Было:** любая задача репо со `[status: in-progress]` отклоняла `git add`/`git commit` во всём репо и на любой
  ветке. Блок «Force-прогон» любой задачи разрешал автокоммит всем. На живых репо: задача, брошенная полтора
  месяца назад, блокировала коммиты, а смёрженная force-задача снимала запрет для соседних.
- **Стало:** задача привязана к ветке. Первым делом смотрится ``Ветка: `<branch>` `` в шапке STAGES.md: `origin/…`,
  SHA и хвосты «отведена от `dev`» / «→ PR в …» не в счёт, а явное `Ветка: master` в репо без PR-флоу — в счёт.
  Без этой строки — тикет в имени ветки.
- **Статус этапа не важен:** ветка задачи охраняется целиком. Раньше хук срабатывал только на `[status: in-progress]`,
  который ни один скилл не ставит, а `/stage-check` закрывает этап в STAGES.md раньше, чем готовит коммит, — мимо
  хука проходил ровно коммит этапа: в обычном режиме агент коммитил сам, в force — без floor-guard.
- **floor-guard на force-коммите — по тому, что войдёт в коммит:** индекс, пути из `git add` той же команды
  (с учётом `cd`), все отслеживаемые при `-a`/`-u`, всё дерево — только при `git add -A` без путей. Раньше смотрелось
  всё неотслеживаемое: сохранённая страница PR с минифицированным JS в корне репо отклоняла любой force-коммит,
  а хук велел чинить её как находку fix-loop.
- STAGES.md, не менявшийся 21 день, хук не видит. Вернулся к задаче — первый kickoff или check обновит файл.
- Worktree без `.claude/` берёт конфиг из основного дерева.
- `cd ../kit && git commit` и `git -C ../kit commit` проверяются по состоянию того репо, куда идёт коммит.
- Блок «Force-прогон» закрывается словом «завершён» в заголовке, `/stage-force` делает это на выходе.
- Команда разбирается лексером:
  - `grep "git add"`, heredoc и сообщение коммита со словами «git commit» больше не отклоняются;
  - `git -c k=v commit` и `git --no-pager commit` больше не обходят проверку.
- `task_path` понимается в бэктиках, с `~` и с плейсхолдером `<ТИКЕТ>/`. Статусы `in-progress — …` и
  `in progress` распознаются.
- session-start показывает задачу текущей ветки первой и до двух недавно тронутых. Про свёртку напоминает,
  только когда архивация реально уменьшит файл: раньше хук и архиватор мерили в разных единицах, и напоминание
  не уходило никогда.
- floor-guard, который упал или не успел, больше не читается как «нарушения»: коммит проходит,
  пользователь видит предупреждение.

### floor-guard — без тупиков в force

На ветках живых репо — до 25 ложных нарушений на репо. В force часть из них заблокировала бы коммит,
и обосновать исключение было негде (например, в JSON).

- Тест определяется по имени файла, а не по сегменту `test/` в пути: доменный модуль «тесты» читался как удалённые тесты.
- Удалённый тест — не нарушение, если вместе с ним удалён проверяемый код или тест перенесён.
- Ассерты считаются по сумме тестов дифа: тест, разнесённый по двум файлам, их не теряет.
- `.catch(() => null | undefined)` — не заглушка. Пустой catch и приведение типов в тестах и моках — не нарушение.
- `# noqa` и `# type: ignore` считаются подавлением, только если в репо есть Python-линтер или тайпчекер.
  С причиной (`# noqa: BLE001 — причина`) — обоснованное исключение.
- Пороги покрытия ищутся только ключами в конфигах тест-раннера, baseline — только в конфиге пайплайна.
  Версии зависимостей в `package.json` больше не «пороги».
- Плейсхолдеры секретов (`…EXAMPLE`, `XXXX`, `0000`) не считаются секретом; `model.fit()` — не фокус теста.
- Раньше молча пропускалось:
  - путь с пробелом — правила не применялись;
  - `diff.mnemonicPrefix`, `diff.noprefix`, `diff.renames` в git-конфиге разработчика ломали пути;
  - новый `floor-ok-file:` в продовом файле глушил весь файл. Теперь маркер действует в тестах и фикстурах
    или если он был в файле до дифа.
- Падение на вложенном репо, субмодуле, симлинке на каталог или на дифе больше 64 MB — теперь код 2, а не 1.
- `--pathspec-from-stdin` — только переданные пути (так зовёт хук). Без него нарушения в неотслеживаемых файлах
  помечены «не в git»: файл, который этап не создавал, — строка в резюме, а не находка fix-loop.
- `scripts/floor-guard-test.mjs` — 32 кейса, 15 из них — формы из живых репо. Прежняя версия проваливает 12.

### archive-stages и retro — по живым файлам

- **Архивация проверена на копиях 90 STAGES.md:** ни одна строка не потеряна, повторный прогон ничего не
  меняет. Сжатие: 273 → 97 KB, 188 → 92 KB, 174 → 86 KB.
- Журналы не архивировались вовсе: `\b` в JS-регэкспе не видит границу кириллического слова, и `## Журнал`
  не находился.
- Даты `DD.MM.YYYY` понимаются.
- Подзаголовки `###` в журнале остаются на месте; группа, из которой уехали все записи, уезжает вместе со своим текстом.
- В свёрнутом этапе остаются `Решения:`, `Коммит`, `- [x] commit:`, незакрытые `- [ ]`, `[live: …]` и `⏳`.
- Этапы внутри «Force-прогона» и «Журнала» не трогаются. «ОТМЕНЁН» — закрытый статус. Размер считается в байтах.
- **`metrics:` пишется в журнал, а `retro.mjs` искал её в блоке этапа** — из N этапов засчитывался один.
  - В строке теперь есть `stage=N`; у старых записей этап берётся из самой записи журнала.
  - `diff=+A/-R`: корзины размера — по добавленным строкам.
  - `diff=—` больше не роняет скрипт; `### Этап 2.1` — отдельный этап.
  - Засчитываются отчёты со старыми именами (`deps-`, `i18n-`, `converge-`).
- `scripts/hooks-test.mjs` — 82 проверки хуков, охвата коммита, разбора шапок, архивации и ретро, гоняется в CI.
  Раньше на эти скрипты не было ни одного теста, а почти все найденные дефекты сидели именно в них.

### Тексты — короче и без противоречий

- **Таблицы «Отговорки» удалены** из stage-check, stage-force и stage-implement: строки повторяли правила тех же
  файлов. Единственное новое правило — «severity ставит чекер; исчерпанный fix-loop с critical — эскалация» —
  перенесено в stage-check, Шаг 3. Размер: stage-check 30.1 → 29.5 KB, stage-force 20.9 → 19.6 KB,
  stage-implement 6.6 → 5.4 KB.
- **Force быстрее:**
  - `lint`, `type_check` и `floor-guard` гоняет только `stage-implement`; оркестратор берёт итог из сводки,
    коммит страхует хук;
  - починенное перепроверяется точечно по `file:line`, субагент чекера — только для визуала и рантайма;
  - красный тест до фикса — только в сценарии root-cause.
- `review_model` определён одним местом (stage-check, Шаг 3.3): модель, отличная от той, что писала код.
  На Opus-сессии в обычном режиме это sonnet.
- Отчёты всех чекеров — `<checker>-<stage>.md` / `-branch.md`. dedup-pass слит с whole-branch pro-review.
  `/compact` больше не описан как действие модели.
- `root-cause` находится по фразе «фикс не помог — разберись»: открытая находка 0.10.0 закрыта.
- `/pipeline-init` ищет `bundle_size`. ROLLOUT — раздел «Хуки».
  Шпаргалка и дек: `stage-implement` в таблице агентов, репо публичный.
- CI:
  - validate видит «21 скилл» и «22 скилла», не принимает SHA-256 и ISO-8601 за тикеты, проверяет путь `headersHelper`;
  - routing требует хотя бы одну фразу на каждый скилл;
  - release-check требует, чтобы версия выросла, а не просто поменялась.

## 0.10.0 — 2026-09-24

Сверка с [addyosmani/agent-skills](https://github.com/addyosmani/agent-skills): оттуда взяты не скиллы, а механизмы,
которых у пайплайна не было, — планка качества, которую нельзя тихо опустить, проверка маршрутизации скиллов,
второе мнение другой моделью и явные отговорки. Всё, что можно исполнить скриптом, исполняется скриптом.

### ⚠ Что сделать на апгрейде

- **Перезапуск Claude Code** — хук `git-guard` теперь гоняет `floor-guard` на force-коммите.
- **`review_model` в `pipeline.config.md`** (секция `## Models`) — модель whole-branch `pro-review` и свежего прогона
  чекера. Поля нет — используется `opus`. Дописать руками или перегенерировать `/pipeline-init`.
- **Строка `metrics:`** получила поля `floor=` и `diff=`; старые записи `retro.mjs` читает как раньше.

### `floor-guard` — планку качества нельзя опустить молча

`scripts/floor-guard.mjs` смотрит на диф (рабочее дерево + неотслеживаемые файлы против HEAD, или вся ветка с
`--base origin/<main_branch>`) и ловит ходы к зелёному без починки: заглушённый чекер (`@ts-ignore`, `eslint-disable`
без причины), `as any`, `.skip`/`.only`, убранный ассерт и удалённый тест, заглушку и пустой `catch`, ослабленный
tsconfig/eslint/порог покрытия, поднятый `baseline` в конфиге, секрет в коде (значение не печатается).
Код 2 — «не смог посмотреть», а не «чисто». Обоснованное исключение — `floor-ok: <причина>` или идиоматичное
`eslint-disable … -- причина` / `@ts-expect-error причина`: не нарушение, но выводится отдельно и уходит в
«⚠ Ожидают подтверждения»; `@ts-ignore` и секреты исключением не бывают. Файл с намеренными дефектами
(фикстуры тестов) — `floor-ok-file: <причина>` в первых строках: его находки выводятся исключениями, секреты — всё равно нарушением.

- В force хук `git-guard` отклоняет `git commit` с нарушениями — там код пишет модель, проверяют модели, и больше
  никто не мешает опустить планку.
- `/stage-check` гоняет его на каждом этапе (нарушение — major-находка в fix-loop), `stage-implement` — перед
  возвратом, финальные проверки — по всей ветке (новый пункт чеклиста `floor-guard`).
- `scripts/floor-guard-test.mjs` — 12 фикстур, гоняется в CI.

### Маршрутизация скиллов проверяется

- **`scripts/routing.mjs` + `evals/routing.json`** — бесплатно и в CI: 36 фраз, которыми просят скиллы, TF-IDF по
  описаниям с грубым русским стеммингом; фраза должна найти свой скилл в топ-2, первым — не реже 75%; пара описаний
  с близостью > 0.5 — ошибка. Первый же прогон нашёл дыру: `figma-compare` не находился по «сверь вёрстку с макетом
  в фигме» — в описании было только латинское «Figma». Описание поправлено.
- **Живые кейсы `kind: "routing"` в `scripts/eval.mjs`** — модель с плагином получает обычную фразу, из потока
  событий берётся первый вызванный скилл плагина. Четыре кейса: `root-cause`, `stage-check`, `figma-compare`
  и «мелкая правка не тянет оркестратор». Первый прогон: «фикс не помог — разберись» решается без `root-cause`
  (модель чинит сама) — открытая находка по описанию скилла.

### Второе мнение другой моделью

Весь код force-прогона пишет `stage-implement` на sonnet, и проверяли его чекеры на sonnet. Финальный whole-branch
`pro-review` и свежий прогон чекера в fix-loop теперь идут на `review_model` (по умолчанию `opus`): та же модель
делит с автором слепые зоны.

### Отговорки

В `stage-check`, `stage-force` и `stage-implement` — таблица «отговорка → на самом деле» из реальных ходов,
которыми этап закрывался неправдой: PASS без значения, «/compact между этапами», `git add` для подготовки,
понижение severity на исчерпанном fix-loop, `floor-ok` вместо починки.

### Недоверенный контент

`references/untrusted-content.md`: DOM, консоль и сеть страницы, HTML прототипов, текст Figma, документация
Context7 и вывод ошибок — данные, а не инструкции. Навигация только по dev-URL и URL из промпта, `evaluate_script`
без cookies/токенов и запросов наружу, секреты не копируются в отчёты. Особенно важно для `devtools-verify`: он
работает в профиле, который пользователь залогинил руками.

### Размер этапа и тесты

- `/stage-plan`: ориентир ~300 строк дифа на этап, больше ~1000 — делить; рефакторинг — отдельным этапом.
  `/stage-check` берёт размер из первой строки `floor-guard` и пишет риск в резюме; `retro.mjs` показывает находки
  и раунды fix-loop по корзинам размера (≤300 / 301–1000 / >1000).
- `pro-review`: рост уже большого файла вместо выноса и рефакторинг, который не уменьшает число понятий, — находки.
- `/root-cause`: при наличии `test` в конфиге дефект логики доказывается красным тестом до фикса и зелёным после;
  откат остаётся для визуального и рантаймного.

### Скиллы легче

Из `stage-check` вынесены преflight окружения и формат сообщения коммита
(`skills/stage-check/references/{preflight,commit-message}.md`) — иначе новые правила не помещались в бюджет 30 KB.

## 0.9.0 — 2026-09-24

Первый релиз, собранный по числам из живых задач, а не по памяти: 30 задач и 182 этапа в четырёх репо
прогнаны новым `scripts/retro.mjs`. Главное, что он показал, — правила, записанные прозой, там, где
их исполнение ничем не проверяется, не держатся. Поэтому большая часть релиза — перевод таких правил
в скрипты, хуки и проверки.

### ⚠ Что сделать на апгрейде

- **Перезапуск Claude Code** — у плагина появились хуки (`hooks/hooks.json`), они подхватываются при старте.
- **`main_branch` в `pipeline.config.md` — ветка, В КОТОРУЮ идёт PR.** Если PR открываются в `dev`, там должно
  стоять `dev`: от него считается whole-branch `pro-review`, `dead-code`, `task-converge`, `task-wrapup`.
- **Раздутые STAGES.md** — прогоните `node "$PLUGIN/scripts/archive-stages.mjs" <task_dir>/<TICKET>/STAGES.md`
  (без `--apply` — только показ). Хук SessionStart напомнит сам, если файл больше 40 KB.
- **Команде — перечитать ROLLOUT.md**: Context7 — внешний сервер, раздел «Что знать до раскатки» дополнен.

### Финальный whole-branch `pro-review` — на самом деле whole-branch

Агент `pro-review` был жёстко ограничен дифом этапа — финальный прогон через агента ревьюил не ветку,
а последний этап. Теперь у агента два режима: stage (дефолт из `/stage-check`) и whole-branch (финал перед
PR). База whole-branch — `origin/<main_branch>` после `fetch`: отставший локальный `dev` тянул в диф чужие
смёрженные коммиты. В `/stage-force` финальный список проверок whole-branch ревью не содержал вовсе —
добавлено.

### `/stage-force` не копит контекст между этапами — субагент `stage-implement`

`/stage-force` велел «сделать `/compact` и идти к следующему этапу», но `/compact` — команда пользователя:
модель её не вызывает ни тулом, ни хуком, и шаг молча не выполнялся — контекст рос весь прогон, пока его
не сжимал сам Claude Code на переполнении. Теперь код этапа пишет новый агент **`stage-implement`** (maker,
чистый контекст), раунды fix-loop — он же в режиме fix; оркестратор держит только STAGES.md и сводки.
Тот же механизм, что уже работал для чекеров. В обычном режиме после этапа по-прежнему предлагается
`/clear` — его вводит пользователь, а новую сессию сориентирует хук session-start.

### ⚠ Context7 требует ключ — обещание «работает анонимно» из 0.8.0 больше не верно

Хостед Context7 без авторизации отвечает `401 Authentication required` уже на `tools/list`, а Claude Code
после такого ответа кэширует сервер как needs-auth (`~/.claude/mcp-needs-auth-cache.json`) и молча к нему
не подключается. Итог — чекеры без предупреждения работали в режиме «не сверено с доками». Нужен бесплатный
ключ `ctx7sk-…` (`export CONTEXT7_API_KEY=...`) или OAuth через `/mcp`. `context7-headers.mjs` теперь
шлёт стандартный `Authorization: Bearer <key>`; `/pipeline-doctor` проверяет ключ curl'ом и находит
застрявшую запись в кэше needs-auth; ROLLOUT — ключ в онбординге разработчика. Найдено eval-прогоном
`docs-lookup`: без доступа к Context7 агент выдал 58 строк ответа по памяти вместо «недоступен» — контракт
агента ужесточён (не больше трёх строк, ни одного утверждения про API).

Схема «оркестратор — Opus, implementer — Sonnet, чекеры — Haiku» проверена на eval-кейсах, 3 прогона на

## 0.7.0 — 2026-09-01

### Новый скилл `/root-cause` — отладка до причины

Пайплайн умел находить дефекты (чекеры) и требовать их починки (fix-loop), но нигде не было написано,
**как** искать причину, когда она неочевидна. На практике это значило угадывание: правка наугад,
симптом погас, две итерации потрачены до того, как причина вообще была названа.

Скилл ведёт от симптома к причине и не даёт назвать дефект исправленным, пока причина не названа:

- **Сначала окружение, потом код.** В монорепо с линкованными пакетами большинство «необъяснимых»
  дефектов лежит не в дифе. Прецедент: симлинк на локальный чекаут UI-кита при запиненной версии —
  две ошибки `type_check` и пропавший индикатор прошли шесть этапов и три чекера на каждом.
- **Улики на границах до гипотез** — источник → спека → код → сборка → рантайм, и отдельно
  API → стор → пропс → шаблон. В рантайме мерить числами, а не скриншотом.
- **Трассировка назад до истока** плюс проверка радиуса будущего фикса: правка в истоке — это правка
  общего модуля, у неё есть импортёры вне области задачи.
- **Доказательство фикса откатом** — красно-зелёное без тест-раннера: откати фикс, симптом обязан
  вернуться. Не вернулся — чинил не то, совпало по другой причине.
- **Три неудачных фикса = вопрос к архитектуре**, а не четвёртая гипотеза. Эскалируется как
  архитектурный вопрос со списком того, что вскрыла каждая попытка.
- Таблица типовых фронтенд-симптом-фиксов: `!important`, `nextTick`, `?.` поверх ошибки типов,
  бамп `key`, лишний `watch`, `z-index: 9999` — и что каждый из них на самом деле маскирует.

Точка входа — `/stage-check`, Шаг 3: первая правка не сработала или причина неочевидна → сюда,
а не вторая правка наугад. Отдельно вызывается на белой странице, `ReferenceError`, hydration mismatch
и «на моей машине работает».

## 0.6.0 — 2026-09-01

Три структурные дыры, каждая из которых пропускала свой класс правок до ручного ревью PR.

### Дубли между этапами ловятся в плане, а не в PR

`/stage-plan` получил **Шаг 2.1 «Скан пересечений этапов»** и парную таблицу «Общие элементы»

её первым источником инвентаря.

### `PASS` обязан нести замеренное значение

Контракт `AC-*` требовал доказательство только от `FAIL` — голый `PASS` был неотличим от «не посмотрел»,
и отличить их постфактум было нечем. Теперь `AC-2.4 — PASS, радиус 12px (Button.vue:34 ↔ node 12:445)`,
а критерий, до которого чекер не добрался, помечается `не проверено`. Правило контракта отчёта:
дополнительной перепроверки силами оркестратора не вводит, шага в цикл не добавляет.
Затронуты `stage-check`, `pro-review`, агенты `figma-compare` / `devtools-verify` / `proto-compare`.

### Третья попытка fix-loop — свежим чекером, а не оркестратором

Было противоречие внутри самого `/stage-check`: Шаг 1 требует чекеров с чистым контекстом («проверяющий
не должен унаследовать уверенность автора»), а Шаг 3 отдавал перепроверку собственных фиксов оркестратору.
После двух раундов он перепроверяет уже не код, а свои попытки. Теперь: 2 итерации оркестратора,
затем **свежий субагент того же чекера** — в промпт идут только несошедшиеся `AC-*`, без истории
неудачных фиксов. Не сошлось и там — эскалация с обоими вердиктами: их расхождение показывает,
чинили ли не то, что проверяли. В `/stage-force` правило то же.

### Мелочи

- `/stage-force`, Шаг 0: зависимые вопросы не идут в один батч — сворачиваются в родительский условием
  или уходят условным допущением. Точка сбора в force одна, переспросить негде.

на порядок флагов, поэтому она разрешала `rm -f -r <любой путь>` без подтверждения, во всех проектах.

### Исправлено

- **`permissions.mjs --check` больше не даёт ложный зелёный.** Запись, которую нельзя дописать из-за
  собственного `deny`/`ask` пользователя, считалась «не отсутствующей»: скрипт печатал `⚠ конфликт`
  и тут же `✔ разрешения на месте` с кодом 0. `/pipeline-doctor` на этом рапортовал OK об окружении,
  где чекеры заблокированы, — ровно тот ложный «сломался пайплайн», ради которого пункт и заводился.
- **Права на удаление сузились до артефактов сборки.** `Bash(rm -f *)` убран; артефакты перечислены
  точными именами (`rm -rf .next`, `dist`, `node_modules`, `coverage`, `.turbo`, `.nuxt`, `build`, `out`).
- **Паттерны `Bash(...)` приведены к префиксной семантике.** Пробел перед `*` литеральный, поэтому
  `Bash(rm -rf dist *)` не покрывал `rm -rf dist`, зато покрывал `rm -rf dist /чужой/путь`,
  а `Bash(curl -s http://localhost *)` не покрывал `curl -s http://localhost:3000/` — самый частый вызов
  в `devtools-verify`. Правило записано в `$comment` профиля, чтобы проектные записи не повторяли ошибку.
- **Группа `fs-read` стала действительно read-only.** `sed`, `awk`, `find`, `xargs` вынесены в отдельную
  группу `shell-tools` с честной подписью: `sed -i` пишет файл, `find -exec`/`xargs`/`awk system()`
  запускают произвольную команду. Набор без `shell-tools` теперь можно отдавать как «только чтение».
- **`pkill` переехал в `ask`.** По маске он снимает не только свой dev-сервер. `kill` по PID остался в allow.
- **Битый `settings.json`** даёт понятную ошибку и код 2 вместо стека Node.
- **`--check` и `--apply` вместе** больше не выполняются молча как один `--check`.

### Добавлено

- **`retired` в профиле разрешений** — список записей прошлых версий с объяснением, чем каждая плоха.
  Скрипт находит их в чужом `settings.json` и предлагает снять руками; `/pipeline-doctor` их показывает.
  Раньше апгрейд профиля был односторонним: новое доливалось, старое оставалось навсегда.
- **`AC-*` в шаблонах отчётов чекеров.** Колонка `AC` и секция «Критерии этапа» в `figma-compare`,
  `proto-compare`, `devtools-verify` и `pro-review`. До этого требование ссылаться на ID жило одним
  предложением в `/stage-check`, а сами чекеры показывали шаблон без ID — контракт держался на памяти
  оркестратора и ломался ровно тогда, когда нужен: на второй итерации fix-loop.
- **`Read(**/.env)` и `Read(**/.env.*)` в `ask`** — секреты проекта больше не читаются молча.
- **Проверка заявленных чисел в `scripts/validate.mjs`.** «Должен показать N скиллов, M агентов» и версия
  в прозе сверяются с содержимым плагина по README, чит-шиту и деку. Числа протухают ровно в том коммите,
  где добавили скилл: сам он проходит, а витрины начинают врать — теперь врут заметно.
- **Правило выбора карты фичи.** Нашлось несколько `FEATURE-MAP.md` по одной фиче — берётся одна,
  с самым свежим `База:` (по дате коммита SHA, не по дате в шапке), и в резюме называется тикет-источник.
  Без правила копии множились без признака, какая из них ведётся.

### Уточнено

- **`deny` в профиле честно назван защитой от случайности, а не границей безопасности** — в README,
  в `/pipeline-init` и в самом профиле. Профиль разрешает `node`/`npx`/`python3`, то есть произвольное
  исполнение; обойти любой запрет из списка тривиально. Кому нужна настоящая граница — нужен sandbox.
- **Презентация догнала плагин**: 17 скиллов, 10 агентов, v0.5.0, `task-converge` в обоих каталогах,
  механика `AC-*` и шаг с разрешениями. В 0.3.1 дек и чит-шит приехали уже устаревшими — в том же
  коммите, который их устарил.

## 0.3.1 — 2026-08-28

Три коммита под одним номером — версия не бампилась дважды.

- **Критерии приёмки получили ID и верификатора.** `AC-<этап>.<n>` + тег `[verify: …]` / `[live: user-side]`.
  Из этого следуют таблица «Покрытие дизайн-источника» (экран не теряется молча), ссылки на ID в отчётах
  чекеров и механическая сборка `TEST-PLAN.md`. Критерий без верификатора — дефект плана.
- **`/task-converge` — новый скилл и агент.** Единственная проверка, которая не смотрит в диф: сверяет
  состояние кода на HEAD с намерением всей задачи и классифицирует зазоры как `missing` / `partial` /
  `contradicts` / `unrequested`. Критерий, который не взял на себя ни один этап, в дифе не появляется —
  его отсутствие невидимо по определению. Находки уходят догоняющими этапами append-only в `STAGES.md`.
- **Гейт качества критериев в `/stage-kickoff`** — пять вопросов к формулировкам до sign-off, а не после.
- **Таксономия вопросов в `/stage-force`** — фиксированный список категорий со статусом
  Ясно / Частично / Не покрыто, потому что батч интервью в автономном прогоне единственный.
- **Шапка «Ориентация» в `FEATURE-MAP.md`** (≤25 строк) — чекеры берут пути из неё, не читая карту целиком.
- **`База: <sha>` в карте фичи** — вторая задача по той же фиче обновляет карту по `git diff <sha>..HEAD`
  вместо повторного чтения репозитория.
- **Статические анализаторы в чекерах.** `dead-code` и `deps-audit` начинают с прогона объявленного
  в конфиге тула (knip / ts-prune / depcheck / madge), если он есть; его вывод — кандидаты, процедура
  подтверждения остаётся. Ставить зависимость ради чекера запрещено — это решение владельца репо.
- Презентация: дек и чит-шит.
