01Problemwhy this at all

Five pains that repeat on every big task

Context

The task doesn't fit in one session

A multi-screen redesign is dozens of sessions over weeks. The model doesn't remember yesterday, the human retells the same things, decisions get made again and differently.

Slicing

Design is fed in by hand, piece by piece

"Here's this component. Now this screen. Now its state". Cutting a multi-screen mockup into manageable pieces and keeping the order is human work, repeated on every task.

Quality

"Done" ≠ done

A margin is off by 6px, hydration broke, toasts are silent, the draft didn't restore. A reviewer, a tester or prod finds it — at the most expensive moment.

Work rhythm

Endless prompting in circles

"Do this. Now this. No, fix the previous one. And put it back as it was". Each round lands as a new diff on top of an unchecked old one: no piece is closed, by evening it's unclear what of the work is still right, and the task doesn't finish — it fades out.

Knowledge

Why it was done this way — nowhere

Two weeks later neither the author nor the reviewer remembers what the fork was and why this option won. In review everything gets explained orally, again.

None of the five is about "the model writes bad code" — all five are about the process around writing code. Now a link to a whole Figma page is enough as input: frames are inventoried on their own, split into stages, and each stage is implemented and checked separately.

Notes This is where to catch the nods: ask the room who has had a review comment like "why 16 here instead of 10". Stress the last point — it's the watershed: the pipeline doesn't improve code generation, it changes what happens before and after it.
02Idealoop engineering

Three principles everything else is built from

01 — Separation of roles

Maker and checker — different contexts

Whoever wrote the code can't check it without bias: they see their intent, not what came out. Each checker is a separate subagent with a clean context: it took no part in the implementation and doesn't know how it was justified.

The side effect turned out more important than the context savings it was done for.

02 — State

The task's memory lives in files

STAGES.md survives /clear, a change of session and a month of work. The plan, decisions, stage statuses, links to reports — on disk, not in context.

One task lived through 42 stages and 76 commits. No session remembered the previous one — and it didn't matter.

03 — Unit of work

Stage = a screen and all its states

Not "build the feature" but "build the photo upload step: default, loading, error, success". A stage opens with a plan and sign-off, and closes with checkers and a commit.

A unit that fits in context whole and is checked whole.

The approach comes from Cobus Greyling's article "Loop Engineering". Everything else is our own pitfalls, laid out as skills.

Notes Key phrase for the room: "a clean-context checker isn't infected by the maker's decisions". We came to subagents to save tokens and got a different quality of findings. If asked "isn't it simpler to ask the model to re-check itself" — answer: we tried, it defends its own decision; a separate agent with no history argues with the code, not with itself.
03Mechanicsone stage's cycle

How one stage goes

Notes Go over the two hard rules of the cycle: don't start implement without sign-off (otherwise edits land mid-stage) and don't close a stage with a critical. The fix-loop is capped at two iterations on purpose: if it hasn't converged in two passes, fixing further blind is pointless. The third attempt isn't a third iteration but a fresh checker subagent with a clean context: after two rounds the orchestrator is re-checking its own attempts, not the code. If it doesn't converge there either, it isn't an implementation bug but a discrepancy in the requirements, and it is taken to a human.
04Mechanicsinputs and context hygiene

What the pipeline uses — and why the heavy stuff stays out of the main context

  • Figma Dev Mode MCP — tokens, node coordinates, screenshots
  • Chrome DevTools MCP — console, live page, measurements
  • git — the stage diff and the whole-branch diff
  • pipeline.config.md — project profile: paths, commands, dev URL, breakpoints, baseline
  • CLAUDE.md — repo conventions; the review rubric lives here, not in the plugin
  • AskUserQuestion — forks are asked in a batch
Notes This answers "won't the pipeline eat our limits". Quite the opposite: subagents cost ~2–3% of usage, and the expensive part is long sessions and bloated files. Hygiene rules: /clear after a stage commit, journal archiving, evaluate_script instead of screenshots for measurements.

Boundary

What must not go into the plugin

One project's rubric in a shared skill gave false Majors in another. Project rules go in CLAUDE.md and pipeline.config.md.

Privacy

Task journals aren't committed

tasks/ is in gitignore: it's the developer's working memory. Only PR.md goes out.

Portability

One config — any stack

Three different stacks run on the same skills. The only difference is pipeline.config.md, which /pipeline-init generates.

Notes If asked "why isn't the journal in the repo" — the story: we tried keeping the whole pipeline in the repository's .claude/, the commit wasn't merged into dev, .gitignore hid the whole folder, and git clean wiped everything twice. Hence the plugin.

Launched by a trigger. No trigger — [skip: no trigger], no subagent is spent. The three narrow checkers deliberately don't overlap with pro-review: it answers for correctness, they — each for its own class of junk.

Project override. The "Checker overrides" section in the config swaps figma-* for proto-* — the rest of the cycle doesn't change, and such a repo doesn't need Figma MCP at all.

Why task-converge is separate. All the others look at the diff and answer "is what was done done right". A criterion that no stage took on never shows up in the diff — its absence is invisible by definition, and only a check against the intent catches it.

Notes Every acceptance criterion in STAGES.md carries a number (AC-2.4) and a tag of whoever is able to check it. Three things follow: a checker report refers to the ID instead of retelling the criterion in its own words; a stage can't be closed with a criterion that has no outcome; TEST-PLAN.md is assembled mechanically, not by rereading all the stages. A criterion with nothing to check it is a plan defect, and it gets caught at kickoff, not after the PR. The main thing about pro-review: it doesn't hand out a list of suspicions. It then tries to refute every finding itself and keeps only what it could write an input → defect scenario for. So its verdict can be read like a colleague's review, not like a linter.

11Practicemanual mode and force

Two modes: where you are in the cycle and where you aren't

Normal mode

Two stops at every stage

  • Kickoff: the agent shows the stage plan and accumulated questions — you make decisions and give sign-off
  • Review: you look at the result with your own eyes before the commit
  • Everything in between — implementation, checkers, fixes — runs by itself

Fits when forks are expensive: a new flow, contested UX, someone else's code area.

/stage-force

The stops are moved to the start

  • All questions for all stages — in one batch at the start
  • Whatever is left is written up as an assumption: "accepted X because Y, reversible via Z"
  • Then implementation, checkers, fixes, commits — to the end of the task
  • Always forbidden: git push, creating a PR, deploy
  • Silent: decides the reversible itself; parks an irreversible fork, an exhausted fix-loop, a red build and a conflict of sources as a blocker and finishes the rest; blockers and accepted decisions go in the summary at the end

The first real run: 7 decisions collected in two batches, 6 assumptions with a rollback, 6 commits.

Force wasn't invented for convenience but from a measurement: waiting at stops took more time than the stages themselves.

Notes Force is the riskiest part, so honestly: it doesn't remove control, it moves it. The prohibitions are hard (no push, no PR), and everything accepted on its own is written in the journal with a rollback path, so any decision can be reversed.

13Demowhat a finding looks like

A real report: pro-review on a task branch

0 critical 4 major 1 minor verdict: Request changes
🟠 major

composables/feature/usePhotoScan.ts:112

isScanning is only the network request's pending: it doesn't cover waiting for the native screen, and the button stays active. A repeated tap starts a second scan() — a second bridge call and a second set of listeners. Native will send one event, both will receive it → two toasts and two analytics sends.

Fix: a busy flag for the whole scan() (guard + finally), isScanning = isBusy || pending.

Also in this run: a camera leak when closing before getUserMedia resolves; the request body is read into memory before the size check; a layer leak between modules.

What was checked

20 files in full, not hunks. type-check — 218, matches baseline. lint clean. Every finding re-checked with an input → defect scenario.

What isn't flagged

A separate block: what the agent deliberately does not flag and why — out of scope, decided by the user, waiting on the backend. Saves an argument in review.

The point

A human finds all four majors too — but in review, a day later, when the context switch already costs a lot.

Notes Point out the specifics: not "a race is possible" but an exact scenario — two taps, two listeners, two toasts, and a fix proposed right away. That's the difference between a linter and a reviewer. And the "not flagged" section — the agent shows the limits of its own responsibility itself.

16Processv0 → v8 in a month

How it was built: each version a reaction to a measurement or a failure

v021 JulA morning prompt "analyze my prompts from past days" + an article on loop engineering → in one morning feature-checker, figma-compare, stage-plan, stage-check were designed. By noon — the first plan from a real Figma.
v122.07Measurement: Figma MCP eats 33% of context → the spec and the comparison became subagents. The side effect proved more valuable: a clean context finds more.
v224.07Measurement: chrome-devtools — 49% of daily usage → the runtime check moved into a subagent too; evaluate_script instead of screenshots; text-fidelity rules against false findings on placeholders.
v324.07Pain: decisions landed mid-stage → stage-kickoff (sign-off before code) and pro-review into the cycle. That's when all project specifics moved into pipeline.config.md.
v427.07An attempt to hand it to the team via .claude/ in the repository: a canonical .mcp.json, /pipeline-doctor, a playbook.
v529.07Measurement: 177M cache-read in 4 days, average context 234k → journal archiving (150KB → 43KB), /clear instead of /compact, the logic-only label — it opened analytics and bug fixes to the pipeline.
v63 AugFailure: distribution via the repo didn't work — the commit wasn't merged into dev, .gitignore hid the folder, git clean wiped everything twice → a plugin and a personal marketplace independent of someone else's .gitignore.
v74 AugRetro of two tasks: a prototype renders several skins from one file, an unresolved cascade gave both false criticals and a missed whole skin → the rule "determine the variant before reading CSS", an element inventory in both directions.
v816 AugMeasurement: waiting at stops is most of the idle time → /stage-force, three narrow checkers launched by a trigger, /task-wrapup → PR.md.

No version grew out of "let's add a feature". All nine came from a number, a complaint or a loss.

Notes This is the most portable slide: the method of building matters more than the tool itself. The scheme is simple — measure /usage, find what costs the most, move it out of the main context; after every task ask "what went wrong and which rule fixes it". Any skill of your own can be built the same way.
17Processwhat to tell the agent

Prompts that really moved the process

Type 1 — bring a fact from outside
“this is what the usage command gave, do we need to improve anything here?”22.07 → checkers became subagents
“other developers may have different names for the figma and devtools mcp”27.07 → canonical .mcp.json + /pipeline-doctor
Type 2 — check before implementing
“let's first check whether there is a delete method”27.07 → there wasn't one, no code was written in vain
“do you check all the files for duplication of logic with what we use in classified”22.07 → dedup became a step of every stage, 11 shared composables
Type 3 — look at the process itself
“Analyze my day by day work prompts and which kind of problems we are solving every day… And how we can automatize our work?”21 Jul, 05:07 → the whole pipeline grew from this prompt
“let's analyze what was done and what was not accounted for”22.07 → a retro on the second day of work

What changed in the second period. Once the pipeline learned to produce work fast, the bottleneck became not "how to do it" but "what not to do". The most valuable decisions were the ones that narrow scope: “we won't do this”, “move to a separate task”, “boundaries: explicitly NOT doing”.

Notes The third type is the rarest and the most valuable: ask the agent to look at your own work. Suggest the room try literally this prompt on their own week — everyone has a repeating step of their own that's begging to become a skill.
18Honestlyweak spots and pitfalls

Where it doesn't work and what cost the most

Lost coverage

The runtime checker is off in core

It conflicts with the live dev server, so I check by hand. The compensation is lint, type-check against baseline, tests, a prod build. It works, but it's a loss of coverage, not an improvement.

Not built

No a11y checker

In the backlog since 24.07, the priority never rose. If a requirement appears — we'll build it.

Boundary

A shared tool ≠ a project norm

One project's rubric in a plugin skill gives false Majors in another. Project rules go only in CLAUDE.md.

The environment cost more than the model's mistakes
  • The dev URL was recorded wrong — :3001 instead of :3000; the checker could have been hitting a dead address for a month
  • "✓ Connected" doesn't mean "tools are available" — Figma MCP is silent without an open file; fixed by restarting the session, not the server
  • A neighboring checkout ≠ the installed package — 0.0.147 in the checkout vs 0.0.151 in node_modules: two :deep() overrides matched nothing
  • yarn build with a live yarn dev kills the dev server; with Vite the esbuild worker dies — every page 500s until restart
  • The type-check baseline drifts — 215 → 216 → 218; measure on git stash, don't trust the recorded number

Each item cost at least one spoiled run — all of them are now in the /pipeline-doctor checklist.

Notes This slide raises trust in the rest. Don't get defensive: say plainly that the main source of critical bugs in core isn't working right now, and that's an open question — either a separate profile and port for the checker, or honestly pin manual checking in the config.

Rules that save time
  • 1 screen + all its states = 1 stage
  • Don't start code without sign-off at kickoff
  • Don't close a stage with a critical or a Request changes verdict
