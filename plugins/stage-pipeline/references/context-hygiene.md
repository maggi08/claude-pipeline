# Context hygiene — the whole task, not only the check

Context is the resource that runs out first. The measurements behind the rules below: the `chrome-devtools` MCP took ~49% of the daily usage while the runtime check ran in the orchestrator; 82–91% of the spend went to sessions with >150k of context; over four days 177M cache-read tokens, 98M of them in one marathon day, an average request context of 234k.

- **Raw Figma dumps do not live in the main context.** The spec for implementing a stage is built by the `figma-spec` subagent (`${CLAUDE_PLUGIN_ROOT}/agents/figma-spec.md`, in prototype repos — `proto-spec`): it gets the node-id and the path `<task_dir>/<TICKET>/specs/<stage>.md`, and returns a compact table (structure, tokens, sizes, states). Direct `get_design_context` calls from the orchestrator are for spot use only, when the subagent loop costs more (one small component).
- **Runtime dumps (chrome-devtools) are not in the orchestrator either.** The `devtools-verify` subagent runs the observation; the orchestrator receives paths to screenshots and a compact report. **Do not make direct chrome-devtools/Figma calls from the main context** — run the recheck in the fix-loop with a subagent too. If they were made anyway (the fallback without an agent, the spot `get_design_context` above), suggest `/compact` to the user right away, without waiting for the end of the stage: snapshots and screenshots are flushed out of the context before they pile up.
- Figma/browser screenshots in the orchestrator — as few as possible: 1 per screen for the eye check; the rest stays inside the subagents. Measure with `evaluate_script` (numbers), not with a screenshot.
- After a stage is closed the user is offered `/clear` (the default) or `/compact` if related work is left in this session (`/stage-check`, Step 4.5); in `/stage-force` isolation does their job: `stage-implement` writes the stage, checkers verify, summaries go to the orchestrator. **`/clear` when moving to an unrelated task** (a new ticket, a retro, a separate bug) — do not drag in the context of the previous one.
- Read large trackers selectively — the current stage by offset/grep, not the whole file. Closed stages and the old journal are folded by `scripts/archive-stages.mjs` (`/stage-check`, Step 4.2); the SessionStart hook reminds you when STAGES.md goes over 40 KB.
- **Open questions for design/product go into one tracker** `<task_dir>/<TICKET>/DESIGN-QUESTIONS.md`, not one by one into the journal of each stage: that way they are closed as a batch instead of being reopened at every step (the year format, the order of placeholders, the consent checkboxes came up again and again).
