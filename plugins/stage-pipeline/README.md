# stage-pipeline

A staged workflow for large tasks with a multi-screen design (redesigns, big features): maker/checker with a clean context for the checkers, state kept in files, context hygiene.

Skills and agents come with the plugin and work in any repository; project specifics live in `<repo>/.claude/pipeline.config.md`, which `/pipeline-init` generates.

## Language

- The plugin is written in English: skills, agents, references, scripts and hook messages.
- The language of a task is the line `Language:` in the STAGES.md header. A new task gets it by the user's request, else by `language:` in `pipeline.config.md`, else by the language of the message that started the task.
- Only `ru` and `en` are supported. Russian tasks keep going in Russian as before; hooks and scripts read both languages.
- In chat the model talks to you in your language, whatever the task language is. Commits and PR descriptions follow the language of the repo history (or your request), not the task language.
- Details and the table of service markers: [references/language.md](references/language.md).

## Installation

```bash
claude plugin marketplace add maggi08/claude-pipeline
claude plugin install stage-pipeline@magzhan
```

Without `--scope` it goes into `~/.claude/settings.json` and is enabled in all repositories. If you need it in one repository only, use the same commands with `--scope project`. After the installation, restart Claude Code.

The repository is public — no access rights and no cloning needed. The "marketplace from a local clone" variant (for the machine where the plugin is edited) is in the [marketplace README](../../README.md).

The plugin brings its own MCP servers `figma` (Dev Mode from desktop Figma) and `chrome-devtools` — there is no need to connect them by hand, but Figma desktop must be running with **Enable Dev Mode MCP Server** turned on. Third-party library APIs are checked not by an external service but against the installed package (the types and CHANGELOG in `node_modules` for the version from the lockfile) — no keys and no authorization needed. Environment check: `/pipeline-doctor`.

### Permissions

So that the checkers do not ask for confirmation at every step, the plugin has a ready permission profile (`permissions/base.json`) and a script that merges it into settings:

```bash
PERMS=$(ls -d ~/.claude/plugins/cache/*/stage-pipeline/*/scripts/permissions.mjs | sort -V | tail -1)
node "$PERMS"           # what would be added (writes nothing)
node "$PERMS" --apply   # append to ~/.claude/settings.json
```

(from a Claude Code session the path is shorter — `${CLAUDE_PLUGIN_ROOT}/scripts/permissions.mjs`; the plugin cache is versioned, so in a shell we take the latest version)

The `Skill(stage-pipeline:*)` and `mcp__*` entries are generated from the plugin itself, so a new skill shows up in the permissions on its own. The script only adds what is missing: it does not touch other people's entries, does not put an `allow` over `deny`/`ask` entries already in place, the same or wider ones (it reports a conflict and counts such an entry as missing — `--check` returns 1 on it), and makes a backup before writing. The profile also carries the prohibitions that `/stage-force` stands on: `push`/`reset --hard`/`clean`/`glab`/`pkill`, the write forms of `gh` (`pr create`/`edit`/`merge`/`comment`, an `api` call with a method or a body, `run rerun`, releases and secrets) and reading `.env` go to `ask`; force-push, publishing and deploy go to `deny`. Reading GitHub through `gh` (`pr view`/`list`/`checks`/`diff`, `run view`/`list`, a GET `gh api`) is allowed by the `github-read` group. The `pr` group is optional and is not in the defaults (`--groups <defaults>,pr` or `--all`): it allows `git push -u origin <branch>`, `git push origin <branch>` and `gh pr create`/`edit`, and in place of `Bash(git push *)` asks only for a bare push, `HEAD`, `main`/`master`/`dev`/`release`, a tag, force and a deletion. The skills do not push or open a PR either way, and in a force run `force-guard` denies a push and any `gh`/`glab` call that is not a read, whatever the settings allow. If your settings still have `Bash(gh *)` in `ask` from an older profile, `--check` names it: ask beats allow, so every `gh` call keeps asking until you remove the entry by hand. If you do not need a broad Bash allowlist, `--minimal` allows only skills and MCP. Paths of neighbouring repositories go separately, into the project scope: `--scope project --apply --dirs ../ui-lib,../prototypes`.

The default `js-toolchain` group also allows `uv run` and `poetry run` (a Python backend's tests and linters), and the optional `docker` group (`--groups <defaults>,docker`) allows `docker compose` for a backend whose tests run in a container; `backend-detect.mjs --doctor` names the exact command when it is missing.

The `deny` list in the profile protects against an accidental agent command; it is not a security boundary: the profile allows `node`/`npx`/`python3`/`uv run`/`poetry run`, that is, arbitrary execution, and getting around any prohibition from it is trivial. Whoever needs a real boundary needs a sandbox, not an allowlist.

`/pipeline-init` does the same when it initializes a project (showing the list and asking for confirmation), and `/pipeline-doctor` checks it through `--check`.

Check the environment: `/pipeline-doctor`.

### Hooks

They work only in a repository with `.claude/pipeline.config.md` and stay silent elsewhere, and they look only at the task of the current branch — by the line ``Branch: `<branch>` `` in the STAGES.md header, and without it by the ticket in the branch name. The hook does not see the tasks of other branches: parallel tasks, worktrees and sessions do not get in each other's way, and old abandoned tasks block nothing (a `STAGES.md` that has not changed for 21 days is invisible to the hook).

A task spanning two repositories (core + webview) lives in the task directory of one of them. In the second repository the hooks find it through the registry of task directories (session-start fills it), if the ticket (`ABC-12`) is in the branch name and STAGES.md names this repository.

- **session-start** — at the start of a session puts into the context a status line for the task of the current branch and reminds you to shrink a STAGES.md larger than 40 KB. After a closed force run it names the commits that the journal does not know by SHA, by title or by content (a commit rebuilt without a signature counts as the same one; a commit that names the ticket in its title is no exception after the close — only its SHA or patch-id in the journal clears it, a PR squash "(#17)" is skipped, and so is a `Revert "…"`; this applies only to force runs opened after the plugin (0.18 or later) first saw the task — the day and the runs already there, dated before that day, are recorded in the task snapshot, so a run already going or closed then keeps the old behaviour): on all branches of the task (from the header and with the ticket in the name; squash-merged ones are skipped) and, in the integration branch, during the first 14 days after closing — your commits in the task files under another ticket. This is work done past the checkers; it is run through a catch-up stage. For a recently closed task of another branch such a line arrives once. A task whose STAGES.md cannot be read is listed with the reason instead of its status. Since 0.21.0, on `/compact` or a resumed session in an open force run of the current branch's task it also prints a resume point after the status line: the stage in progress, uncommitted code against the last maker snapshot (paths as the maker left them / changed since), the reports in the commit window with their outcome state, the open blockers and one next action (kickoff, spawn `stage-implement`, run the checkers, fix round or write the "Findings outcome" of a named report, commit, final checks). The whole output stays within 10,000 characters, lists are cut with "+N more"; a `startup` and a closed run print no resume point (`scripts/resume-point.mjs`).
- **git-guard** — on a task branch in normal mode the agent's `git add`/`git commit` are rejected at any stage status: the agent hands over a ready commit message and you commit yourself. In force mode (an unclosed "Force run" block in STAGES.md — without "completed" in the heading) the agent runs `git add` + `git commit` itself, without asking — but the commit goes through `floor-guard` and is rejected if the diff has a silenced checker, a weakened test or a leftover stub. What is checked is what will go into the commit: the index, the paths from the `git add` of the same command, all tracked files with `-a`, the whole tree only with `git add -A` without paths. A force commit is also rejected when a checker finding has no outcome — "## Findings outcome" in the report (`references/checker-report.md`); when the commit deletes a UI component whose name is not in the Parity table of STAGES.md; when the diff has kit overrides (`font-bold`, `uppercase`, `text-[…]`, `rounded-[…]`, `!important`…) and there is no `kit-overrides` report with these files. A force commit in a run opened after the plugin (0.18 or later) first saw the task (the day and the runs already there, dated before that day, are recorded in the task snapshot; a heading dated that day or whose date does not parse counts as new) is also rejected when its window (the reports written after the previous force commit on the branch) has no `pro-review` report, or when UI files changed (`.vue .tsx .jsx .svelte .css .scss .html`) and there is no design report (not needed on a `logic-only` stage; a skip line with `logic-only`, no design source or no visual change stands in for it) or no `devtools-verify` report and no skip line with a runtime reason (`logic-only`, no visual change — a browser, MCP, login or stand reason is not one); a fix commit that touches only the files of the previous force commit passes. In a repo with a `## Backend` section (or one that the task repo's `### <name>` points at) the same window also needs an `api-verify` report when files matching `api_files` changed (tests do not count), or a skip line `no behaviour change — <path:line>`; an environment reason (docker, no network, timeout) is not a skip; an `.html` there is not a UI file when the repo has no dev server url. Each force commit leaves a receipt in the plugin data (`receipts/<TICKET>.jsonl`: sha, tree, reports, counts, skips); the full run digest lists the UI stages committed without a runtime check, the short one shows the count. A commit with a service signature (`Co-Authored-By`, "Generated with …") is rejected on any branch of a repository with the pipeline. On the branch of a task whose STAGES.md cannot be read (see "Task files" below) `git add` and `git commit` are rejected in either mode, with the file and the reason named. Since 0.21.0 a force commit in a run that is new by two first-sight gates (the 0.18 receipts gate and the plan snapshot of plan-check: a Force block there at the first look is a run already going) is also rejected, with "code not written by stage-implement — hand it to a fix round", when a code file (explicit extension list; markdown, JSON, lockfiles and generated files do not count) does not match the last blob a `stage-implement` stop recorded (the blob the command will commit is judged: the working tree for the paths it stages, the index for the rest); a deletion whose path the Force block names passes. The rule fails open for a repo no maker was spawned in, for a run with spawn snapshots but no stop record, and for a run whose spawn snapshot did not finish (a failed or slow `git status` / `hash-object`; symlinks, FIFOs and untracked files over 5 MB are not judged). In such a run a commit command that also changes the index other than by `git add` (`update-index`, `read-tree`, `mv`, `rm`, `reset`, `apply --cached`, `checkout -- <path>`, `restore --staged`, a `GIT_INDEX_FILE=` prefix) is rejected: stage with `git add` in its own call, then commit. `STAGE_PIPELINE_MAKER_RECEIPTS=off` in the environment turns this rule off.
- **agent-guard** — before a subagent starts. A whole-branch `pro-review` without `model` equal to `review_model` from the config (`opus` by default) is rejected. When the config sets the optional `security_model`, a `security-review` call whose model (the `model` parameter, else the agent's own) differs from it is rejected too (an alias and a full id match, as for `review_model`); without the key the security review stays on the agent's own model. Since 0.25.0 a general-purpose agent started for the security review or the ds-parity pass is rejected with the agent to use instead: a general-purpose agent inherits the session's model, and both checks have their own agents on sonnet. The hook tells the check by the call's description ("security" next to review, audit, check, pass or sweep; "ds-parity") or by a prompt that points at the ds-parity skill; a call that does both is split in two, and the other checks of a combined sweep go to their own agents. A call that is not that check passes once its description does not name it. `stage-implement` does not start in a force run until its block has the line `Confirmed: <date> — interview answers` (stage-force, Step 0; no separate "yes" is asked after the interview); blocks opened before 0.12 are not touched. Since 0.21.0 it also (1) denies the spawn of `stage-implement` in implement mode while the stage or the Force block has a new `plan-check` problem (duplicate or unverifiable `AC-*`, an open `[Gap]`/`[Ambiguity]`, a reference that resolves nowhere, a UI stage without `Visual reference:`, a new Force block without `Stage dependencies:` / all 12 `Taxonomy:` categories / a rollback per assumption; old plans only get warnings), and (2) records the tree at every allowed `stage-implement` spawn (repo, HEAD, branch, blob hash of every dirty path) for maker-guard. A spawn from a tree with no current task (a run orchestrated from the main tree while the code is in the task's linked worktree) belongs to the one task with an open Force block whose ticket the prompt names; its tree is recorded in that task's worktree, so git-guard's maker rule finds it there. A general-purpose agent started for the api-verify or contract-compare check is rejected the same way, with the agent to use instead.
- **force-guard** — before a Bash command in a force run. A call that would stop on a confirmation is rejected at once, with an explanation, instead of waiting until you come back to the terminal. These are `pkill`/`killall` (the agent stops its process by PID) and subcommands under `ask` in the user and project settings (`git push`, `reset --hard`, `gh`…), which the agent records as run blockers. Outside force the hook is silent: you are nearby there, and a question is a normal part of the work. One rule holds in and out of force, and in a repo without a pipeline config: a subagent that is one of the plugin's agents (a checker, the maker) is denied a `git push` and every `gh` / `glab` call that is not a read — push and PR are the orchestrator's or yours; the main thread and other agents are not touched. A help or version call, a clone, a download, a graphql query that is not a mutation, a dry-run push and a push to a local path are not publishing, for this rule and in force alike. In an open force run it also rejects a command that names the plugin data directory (journal-gate does the same for an Edit / Write / MultiEdit of a file there): the maker records, plan snapshots and receipts there are written by the hooks only.
- **journal-gate** — after an edit of STAGES.md or of a report in `checks/`. For a Bash call it acts only when STAGES.md or a report changed during the call (a `cat`, `ls`, `grep`, `sed -n` or `run-digest` of the journal stays silent); a PreToolUse run of the same script stamps the files of the current branch's tasks and of the tasks the command names by path before the call. Before an Edit or Write of a task file a PreToolUse run takes the task snapshot when there is none yet, so the first look reads the journal before the edit. Outside a pipeline repo both runs leave at once (a file-system check, no git). Returns violations to the agent in the same turn:
  - in the journal: a criterion tagged `devtools-verify`/`figma-compare`/`proto-compare`/`api-verify` is closed ✅ while the outcome names another checker or nobody (`ac-checker`); a design checker is skipped for a browser reason; ✅ with a caveat ("not captured", "code only"); "not verified, no data" instead of staging the state; "like X" in a criterion or a decision without `path:line` of X; a checker marked `[x]` while the outcome of its findings is incomplete; a `[verify: staging]` criterion marked done without the staging address, route and what was observed (`staging-no-observation`);
  - in a new journal line or a report written after 0.18 (with or without an `AC-*` id): every unquoted bare `[live: user-side]` — the honest form is `[live: user-side — <prerequisite>; <route> → <observed>]`; a mention in backticks is a quote, older lines and reports are not touched;
  - in a report written after 0.18.0, a `false` outcome without a proof of its own kind ("the fix is impossible", "not reproduced" without two attempts and the route, "the stage did not change it" without a base sha, a plan line for "a later stage owns it", the report itself as the basis, a sample for "false for the data", "not related" without a diff), and a critical dismissed as `false` without a cited fresh report on `review_model` in `checks/`;
  - in the journal, a new line of "Awaiting user confirmation" or under `Assumptions:` of a Force block without `Rollback: <cost>` and `Basis: <path:line | node-id | quote | guess>`; the digest lists them by rollback cost;
  - in a devtools-verify report written after 0.20 (a report already on disk when 0.20 first saw the task stays valid): the `map:` line in a repo with a verify map; a PASS on a criterion tagged `[effect]` (or its Russian tag) without the request (`METHOD /path … status`) and a read-back (after a reload or from a second view); a `fixed` outcome without a re-run artifact that exists (`checks/devtools-verify-<stage>-r<k>.md`, `-fresh.md` or a `checks/screens/` path);
  - in an api-verify report written after the release: a PASS on a criterion tagged `[verify: api-verify]` without the request and its response code (`GET /… → 200`) and a `read-back:` / `control:` line (`no-api-proof`; a qualifier that says the step was not taken, «read-back as A not done:» or «control in this run skipped:», is not one); a `fixed` outcome without a re-run report that exists (`checks/api-verify-<stage>-r<k>.md` or `-fresh.md`, `no-rerun`); in a task with a `## Backend` section, a `false` outcome that hands the finding to the backend ("belongs to the backend", "backend owns it") is a weak dismissal even with a contract line: the backend is part of the task
  - in a report: PASS without a measurement; no line `Findings: critical N · major N · minor N`; an outcome "leaving it", "awaiting", "long-standing" without a check on the base; for devtools-verify — no `geometry` lines, for a stage with a "Visual reference" — no `style-diff` lines, and in a report written after 0.18 no `doctor:` line (what verify-doctor printed) or no `auth:` line (whether the browser was logged in; the Russian keys are in `references/language.md`);
  - closing a "Force run" block as "completed" while blockers are open, findings have no outcome, the CI gate on the HEAD of the task's worktree is not green (since 0.25.1 the worktree where the task's branch is checked out, when the close is written from another one) (a `skip:` line of the Force block covers a gate that cannot run here, never one that ran red on HEAD), or (runs opened after 0.18 first saw the task) the whole-branch `pro-review` or `task-converge` report is missing or older than the last commit that changed the tree (judged in that same worktree since 0.25.1); "completed with blockers" — if every non-green gate is named a blocker, and every missing or stale final report is named by an open blocker with its marker, `[final: pro-review — not run]` / `[final: task-converge — stale]` (the state words in Russian in a ru task; prose about the checker is not read, and in a Force block dated 2026-10-26 or later that was written after 0.18.2 first saw the task (every block already there then, open or closed, keeps the lift words; a second data dir that first reads the task later holds the blocks 0.18.2 wrote) a blocker is lifted only by the field `Lifted: <who> <date> — <answer>` (a who of at most 4 words, the answer after the date; its Russian form is in the marker table), never by a word in the reason; an older block keeps the lift words, and the field on the blocker's own line lifts there too). On closing, the short run summary (`run-digest.mjs`, with the CI gates) is put into the context with the path to the full one, `RUN-DIGEST.md` — the short one goes into the final message whole. Since 0.18.1 the call that closes the block (an Edit or MultiEdit of its heading, a Write of STAGES.md, a Bash call that names the task; a close the hook rejected counts for the same session's fixing edit) also closes the session's MCP browser (`browser-cleanup.mjs --session`, by PID, only this session's pipeline browsers; nothing is held up when `ps` is missing) and both views of the digest carry its line, `Session browser: closed by PID …`. A heading closed by hand, in another session or during an unrelated call leaves the browser open, and so does `STAGE_PIPELINE_BROWSER_CLEANUP=off` in the environment: the line then says `left open — …; close: <command>`. In a task with a `## Backend` section, a task of several repos also needs a whole-branch pro-review report of every other repo it changed (`checks/pro-review-branch-<repo>.md`) before the close.

  It looks only at lines and reports that did not exist when the plugin first saw the task: old stages need not be rewritten.

  Task files: the hooks and scripts read STAGES.md, the archive and the reports only as regular files of at most 4 MB whose real path lies inside the task directory (a task root behind a symlink, `.claude/tasks → ~/.claude/team-tasks`, is fine), and the configs as regular files of at most 256 KB. A STAGES.md or a report that is there but cannot be read (over the limit, a link out of the task directory, not a regular file) counts as open, not as empty: the force commit and the "completed" close are refused with the file and the limit named, and the run digest says "Not ready for PR" for it.
- **frames-guard** — when devtools-verify finishes. It does not let the agent go until it has opened every frame it captured: a defect that the user found after "done" has sat on a frame nobody opened. It also blocks a finish when the first navigation came before a `verify-doctor.mjs` call, or after a doctor result other than `ok` / `no dev url` (`wrong app`, `down`, `no config`, `error`, or no `doctor:` line at all): a run against another worktree's server on the same port is green about the wrong code. Since 0.18.1 it also blocks a finish that leaves running what the agent opened: a page of its `new_page` still in the freshest `## Pages` list (the last page may stay, on `about:blank`: MCP 1.6.0 refuses to close it), or a browser it launched that still runs: a `journey: browser pid N` line or the one PID a `<browser or node script> … & echo $!` call printed, a wrapper such as `timeout`, `env` or `bash -c "…"` included (the browser told by `browser-cleanup.mjs`'s list of executable names, Linux ones included), both from its own Bash results, a browser executable started after the agent's first transcript record (a transcript with no timestamps names none). The page list is read only from the page tools' own `## Pages` section, never from a console message. Only a page that the agent's own successful `new_page` returned as the fresh selected one is named; a tab left by a `new_page` that answered with an error (or with an open dialog) is not, and devtools-verify lists and closes it. Once a page tool of that server answers with the transport's disconnect error (the answer starts with `MCP server "…" is not connected` or `MCP error -32000: Connection closed`; the same words in a page's dialog or in a URL do not count), the page rule is off: nothing can close the page, and the agent names it under "Could not verify". `browser-cleanup.mjs --orphans` closes a temp-profile (`--isolated`) browser that outlived its server; a `stage-pipeline-chrome` browser whose server is gone is only listed: `browser-cleanup.mjs` with no flag names it with `kill <pid>`. The orchestrator's pages and the session's MCP browser are not the agent's. A force run already open when 0.18 first saw the task is not checked for this.
- **The firing log.** Every block or deny of the six hooks above also appends one row per rule the block names to `firings.jsonl` in the plugin data directory (`STAGE_PIPELINE_DATA_DIR`, an absolute path, makes every hook and script use that directory instead — for a throwaway run). A row has the rule ID (`<hook>/<slug>`), the task, the repo path, the time, the tool, whether the call only read, and the event — IDs and paths only, never a command, a file's content or the message. The file is capped at 1 MB: past it, it becomes `firings.jsonl.1` (one older generation, the previous one is dropped) and a new one starts. A log that cannot be written never changes a verdict. `retro.mjs` reads it.
- **browser-admit** — before a DevTools MCP call (the plugin's `chrome-devtools`, the opt-in `stage-pipeline-chrome`, a project's own `chrome-devtools`), with a 300 s timeout. A session without a browser waits here until the machine has the memory for one (the wait is capped at 4 minutes, 240 s — the host's hook timeout forbids an uncapped one — then it goes on with a `browser: waited <s> s for memory, starting anyway` line); a session with a browser, and `normal` mode, pass at once with no output. It never blocks on an error (section 2d).
- **session-wait** — on `Stop`, `UserPromptSubmit`, `PermissionRequest`, `Notification`, `Elicitation`, `SessionEnd` and `AskUserQuestion`: records in `<data dir>/sessions/<id>.json` that the session waits for you and on what, for the tracker page's «Waiting for you». It never blocks and prints nothing.
- **maker-guard** — when `stage-implement` finishes (since 0.21.0). The stop is blocked, at most 3 times per agent, until the hand-back (read from the agent's transcript) has its sections (`Changed:`, `Decisions:`, `Product-visible:`, the checks line, `Not done / blocker:`, `ACs without implementation:`), has numbers in the checks line when the config has a `type_check` command, fits 4000 characters and names exactly the files that changed since the spawn and that the maker wrote (a file it did not write goes under `Not done / blocker:` as `not mine: <path>`). After the third block it lets the stop through with a «hand-back not fixed» item. Every stop that goes through stores the post-run blob hashes and the Product-visible / Not done / ACs items per ticket; the full run digest prints them verbatim under «From the maker's hand-backs». A run that was going when 0.21.0 landed (its Force block was in the plan snapshot of the first look) is not checked. A maker that died before its stop leaves its baseline open: the next spawn on the same HEAD continues from it. Limit: one `stage-implement` at a time per worktree in a force run — parallel makers in one tree cannot be told apart by a tree snapshot, and each blocks the other's hand-back for files it did not write (a maker clears such a block with `not mine: <path>`); no hook enforces it. A stop whose change set cannot be read (a slow or failed `git status`), and a maker-guard killed during the stop, make the commit rule fail open for the run.

### Scripts

- `scripts/force-queue.mjs add|list|remove|check|run` and `scripts/force-run.mjs <repo> <TICKET>` — the night queue of headless force runs (section 2c).
- `scripts/archive-stages.mjs <STAGES.md> [--apply]` — fold closed stages and the old journal into `STAGES-ARCHIVE.md` (called from `/stage-check`, Step 4.2).
- `scripts/run-check.mjs -- <command with {files}>` — a stage's lint/test/type_check/build: only the changed files; on a machine with RAM ≤ 16 GB — admitted by free memory (the order of the tasks counts only under shortage, a wait is capped at 5 minutes) and at a lowered priority (`references/heavy-checks.md`; `--mode` — the machine mode). A whole command on a clean tree records its result under the commit's tree — the hook sees the CI gates through it. `{files:rel}` (or `{files:rel+py}`) gives repo-relative paths instead of absolute ones, for a command that runs in a container where the repo lives elsewhere.
- `scripts/monitor.mjs [--json] | serve [--port N] [--new-token] | open [--port N] [--no-browser] | stop` (`open` and `stop` are what `/stage-pipeline:monitor` runs) and `scripts/heavy-queue.mjs status [--json] | pause|resume <task key> | order <key>…` — the tracker page and the balancer's state and controls (section 2d).
- `scripts/ci-gates.mjs [--run]` — the CI gates from the config (the "## CI gates" table or `e2e`/`smoke` in Commands) and their state on HEAD; `--run` runs the non-green ones through `run-check.mjs`. A gate that cannot run here is skipped on the record: `skip: <reason> <date>` in its table row (or after an `e2e`/`smoke` Commands line), or `skip: <gate> — <reason> <date>` in the run's Force block. It is listed once as skipped and accepted at close; without a reason and a date the mark does not count, and an unmarked gate still blocks. A green run on HEAD beats any skip, and a run red on HEAD beats the Force block's skip (that line stands only for a gate that cannot run here; the user's mark in the config row still counts). Called from the final checks. A copy of the scripts in a linked worktree of the installed plugin's repo records a gate both in its own data directory (`stage-pipeline-inline`, the one a `--plugin-dir` session on that worktree reads) and in the installed plugin's one, and `run-check` says so.
- `scripts/kit-override-scan.mjs [--base <ref>] [--out <report>]` — kit overrides and manual typography in the added lines; with `--out` it writes a `kit-overrides` report in the checker format (every file is major, then "Findings outcome"). The kit directory from `ui_lib` is not scanned; in the kit's own repository — `kit_overrides: off` in the config.
- `scripts/floor-guard.mjs [--base <ref>] [--pathspec-from-stdin]` — the quality floor over the diff (plus the project's own `## Repo rules`, below): silenced checkers, `as any`, weakened tests and configs, stubs, secrets; the first line is the diff size (called from `/stage-check`, `stage-implement` and the hook on a force commit — the hook passes the commit paths through stdin). Violations in untracked files are marked "not in git".
- `scripts/verify-map.mjs --changed [--base <ref>] [--feature-map <file>] | --radius <file>… [--depth N] [--feature-map <file>] | --init [--language en|ru] | --lint <feature-file>` (0.20) — the repo's verify map (`.claude/verify/`): changed pages → routes → map features; the live radius of a shared-module fix (importers up to the pages → routes → features with their primary path; no map: routes only); the README from the config; a feature-file lint.
- `scripts/verify-doctor.mjs [--url … --route … --marker …]` (config keys `verify_routes:` / `app_marker:` in "Dev server") — read-only: is the dev server on the port this worktree's app (answers on the baseline routes, the app marker, the listening process's `cwd` inside the worktree), always one `doctor:` line (`ok`, `wrong app`, `down`, `no dev url`, `no config`, `error`); the config is found as the hooks find it, the main tree's for a linked worktree with `.claude/` excluded; devtools-verify runs it before its first navigation.
- `scripts/browser-cleanup.mjs [--session [--persistent] | --orphans]` — the Chrome windows the DevTools MCP servers launched, by Claude Code session (the nearest `claude` process above the caller). No flag — read-only: this session's browsers with their PID and the close command, other sessions' with age and session folder, orphans, and a `stage-pipeline-chrome` browser whose MCP server is gone (it keeps that profile busy; listed with `kill <pid>`, never closed by the script). `--session` closes this session's pipeline browsers by PID (the plugin's `--isolated` one and `stage-pipeline-chrome`; `--persistent` — only the latter); the next MCP call opens a fresh one; a project server's browser on its own profile (the default or a `--user-data-dir`) is listed, never closed; one started with `--isolated` cannot be told from the plugin's, so it is closed too and relaunches on its next call. `--orphans` closes temp-profile browsers whose MCP server is gone: a browser executable of this user on a `puppeteer_dev_chrome_profile-*` profile in the OS temp dir, never a shell or a script that names such a profile. SIGKILL goes only to a PID whose start time and command line are still the ones read before SIGTERM. Another session's browser is never closed. The force close runs `--session` (journal-gate); in normal mode `/stage-check` runs `--session --persistent` after each stage with the opt-in profile, and names the `--isolated` browser's PID and this command.
- `scripts/journal-check.mjs <task_dir>/<TICKET> [--ledger]` — the same rules as journal-gate, over the whole task, including the archive and `checks/`; `--ledger` adds a summary and the findings outcome in all reports (old tasks have none by construction).
- `scripts/plan-check.mjs <STAGES.md> [--stage N] [--root <repo>] [--json]` — lints the plan before work starts: a summary line per stage (AC count, verifier spread, visual reference, references resolved N/M), then problems, then warnings; exit 1 on problems. The same check backs the agent-guard deny.
- `scripts/run-digest.mjs <task_dir>/<TICKET> [--full | --no-write]` — the summary of the freshest run from the journal and the reports. The full view also lists every critical, major and FAIL dismissal (`false`) verbatim with its checker and sorts "Awaiting" by rollback cost; the short view gives the dismissal count. It writes the full digest to `<task_dir>/<TICKET>/RUN-DIGEST.md` (every line of every category, overwritten at each closing) and prints the short one: blockers, red CI gates and findings without an outcome in full; a "Not ready for PR" line when a report has a critical, major or FAIL finding without an allowed outcome (each outcome line is judged by the severity of its own finding, so a fixed minor does not stand in for a parked critical) or a task file cannot be read; the unverified (by stage), the checkers' "could not verify" and minor as numbers; "accepted on its own" as a number and the first three. `/stage-force` inserts the short one into the final message.
- `scripts/retro.mjs <repo> --findings [--json] [--corpus <tsv>] [--repo <name>] [--root <dir>]` — the input of `/promote`: the critical and major findings of the repo's tasks with their outcomes, a first cut into classes with a recurrence flag (a class recurs when it has hits in two or more tasks), signals (the same path or identifier in two tasks), the commits made on each task branch after the task closed (no checker ran on them), and with `--corpus` the rows of the review corpus for the repo.
- `scripts/promote-proof.mjs --root <repo> --candidate <json> [--json] | --check-eslint` — the proof of a `/promote` candidate: it fires on at least two real pre-fix versions (the files a fix commit changed, at its parent) and stays quiet on HEAD, or fires there only on lines added after the fix. A lint candidate runs on the project's own ESLint (never `npx`) and counts only files ESLint really linted; a Repo rules row runs its regex on `git show` output. Exit 0 proven, 1 not proven, 3 no ESLint.
- `scripts/retro.mjs <repo>` — a retro over the task files: false findings, fix-loop rounds, skips per checker, `AC-*` outcomes, bloated STAGES.md files. Takes metrics from the `metrics:` line of the stage journal. Its «Hook firings» section reads the hooks' firing log (`--firings <file>` another log): blocks and denials per rule, the repeats per task, the rules that fired on reads. Only the rows whose repo lies under the given repo are counted; `--all` is the whole-machine view.

## 0. Once per repository — `/pipeline-init`

Studies the project and creates `<repo>/.claude/pipeline.config.md` (paths, commands, dev URL, design sources, code layout, platforms, `task_path`/`memory_path`). If there is no `CLAUDE.md`, it offers `/init`. It also offers to lay the pipeline permissions into the user scope (see "Permissions" above) — once per machine, not in every repository.

### Backend tasks (overview)

A repo with a `## Backend` section in its config gets backend support; without it nothing changes. The pieces, each described where it works: the section and `backend-detect.mjs` (below, "Backend section"); the contract and the criterion tags (below, "Backend task: contract first"); `api-verify` and `contract-compare` ("Skills and agents"); the force-commit rule for `api_files` and its `api-verify` report ("Hooks", git-guard); the final checks in every repo of a task (`stage-force`, final checks); `deps-audit` for Python manifests.

Two pieces live only in their skill files: the final checks in every repo of a multi-repo task are in `skills/stage-force/SKILL.md` (final checks), and the Python manifests (`pyproject.toml`, `requirements*`, lockfiles) are read by `skills/deps-audit/SKILL.md`. To turn it on in an existing backend repo: `/pipeline-init`, then `/pipeline-doctor`.

### Backend section (optional)

`## Backend` in `pipeline.config.md` turns on backend support for a repo that serves an API (the commands to test and lint it, the files that make up its API, where the contract goes). Two forms: fields right under the heading (this repo is the backend, `path: .`), or one `### <name>` subheading per backend repo, each with its own `path:`; in the second form, fields above the first `###` are defaults inherited by every repo, and a repo's own field wins. A value of `—`, `-` or `none` means "not set". Without the section nothing changes: the pipeline behaves as before. `backendConfig()` in `scripts/hooks/pipeline-state.mjs` reads it; `/pipeline-init` offers it from `scripts/backend-detect.mjs`. An `api_files` glob with more wildcards than the hooks accept is skipped there; `backend-detect.mjs --doctor` names it in a `fail` row (the local config and every `###` repo included).

### Backend task: contract first

In a repo with a `## Backend` section the plan starts with a contract stage: endpoints, roles, errors, events and migrations written once in `references/contract.md`, before any code. The plan carries a "Contract coverage" table (every endpoint, event and migration has a stage); backend behavior is tagged `[verify: api-verify]`, and what needs both sides live is tagged `[verify: staging]` and closes only with an observation on staging. See `references/contract.md` and the stage-plan skill, "Backend task".

## 1. Once per task

1. **`/feature-checker <ticket/feature>`** → `FEATURE-MAP.md` — a map of what already exists (reuse vs write from scratch). Needed for planning.
2. **`/stage-plan`** → `STAGES.md` — splitting into stages (1 screen + its states = 1 stage), WHEN/THEN acceptance criteria, the order. Requires FEATURE-MAP. Input: a ticket, a design source, a contract and/or a `PRODUCT-HANDOFF.md` from the product side (`references/product-handoff.md`; its criteria `H<n>` map to `AC-*` in a "Product handoff coverage" table). With none of them (`plan-check.mjs --input`) it asks one question: plan the task stated in chat, or go to the product side (the intake command of product-pipeline; without it a ticket, design or contract); only the product route writes no plan.

Criteria are numbered (`AC-<stage>.<n>`) and carry a verifier tag — who is able to check them: `figma-compare`, `devtools-verify`, `pro-review`, `user-review`. A criterion that only the user can reach is never pre-tagged at plan time: the checker defers it with `[live: user-side — <prerequisite>; <route> → <observed>]` after it tried (force asks for the login up front). This gives three things that would not exist otherwise: a design source coverage table (no screen is lost silently), ID references in checker reports (the fix-loop knows what it rechecks) and a mechanical assembly of TEST-PLAN.md instead of rereading all stages. A criterion without a verifier is a defect of the plan: there is nothing to check it with.

## 2. The loop of EACH stage

```
/stage-kickoff   → show the stage plan + merge with what has piled up (TODO/DESIGN-QUESTIONS/
                   decisions) + collect business input + sign-off  → runs figma-spec (the spec)
   implement     → write code (reusing what feature-checker found)
   checkers      → in parallel: figma-compare ∥ pro-review (static, subagents)
                   + devtools-verify (runtime, subagent; the dev server is held by the orchestrator)
                   + narrow ones by a trigger: dead-code / i18n-sweep / deps-audit
   fix-loop ≤2   → fix what is confirmed, recheck point by point
   user-review   → show the user, wait for approval (mandatory)
/stage-check     → journal in STAGES.md + commit message
   /clear        → typed by the user (the model cannot call /clear or /compact);
                   the new session starts from the status line of the hook and STAGES.md
```

Rule: do not start implement without a sign-off (kickoff); do not mark a stage done with critical findings, a pro-review verdict of Request changes or open escalations.

The commit message is prepared at EVERY stage — by the substance of the change, not "stage N", and without service signatures about the tool's authorship.

## 2b. Autonomous run — `/stage-force`

The same plan and the same checkers, but the stops are moved to the beginning: all questions for all stages are asked in one batch, then the run goes to the end — implementation, checkers, fixes, commits — without waiting.

The context does not pile up between stages without any `/compact` (the model cannot call it anyway): the stage code is written by the `stage-implement` subagent, the fix-loop fixes by the same one in fix mode, and the checker subagents verify. The main context keeps STAGES.md and short summaries, so a long run goes in one session.

Always forbidden: `git push`, creating and commenting on a PR/MR, deploy, publishing. Always mandatory: a stop on irreversible forks, an exhausted fix-loop, a red build and a conflict of sources of truth. Reversible forks are decided on its own: the revertible option is taken, and a line goes into "⚠ Awaiting user confirmation".

## 2c. Night queue — `force-queue.mjs`

The interview needs you; the run does not. Collect the answers in the evening, leave the runs for the night.

**Your own repos only.** `claude -p --permission-mode auto` runs the repo's project hooks and settings unattended, so a queue entry executes whatever the repo's `.claude/` says. Queue only repos you trust.

**Evening, per task.** `/stage-force <TICKET> --interview-only` runs the interview (Step 0) and writes the Force block with the `Confirmed:` line, but starts no stage and makes no commit. It ends with the command that queues the task (`<plugin>` is the plugin directory on the machine that will run the night):

```
node <plugin>/scripts/force-queue.mjs add <repo> <TICKET>     # only a task with a confirmed interview; otherwise the reason is named. Makes the task's worktree now, so you can prepare it
node <plugin>/scripts/force-queue.mjs list                    # the queue and the status of each task
node <plugin>/scripts/force-queue.mjs remove <TICKET>         # only a task that was not started
node <plugin>/scripts/force-queue.mjs check                   # before the night: every "no" is named, exit 1 on any
node <plugin>/scripts/force-queue.mjs run                     # the queue, one task after another, in the order they were added
```

`run` takes `--threshold 90` (percent of the 5-hour window at which a task waits for the reset before it starts), `--margin-min 5`, `--max-sessions 3` (new sessions in a row without a newly closed stage, then the task stops), `--retries 1`. Each task runs as a headless `claude -p` force session in its own worktree next to the repo (the main copy is not touched; a task branch that is checked out in the main copy is refused: switch the main copy to another branch); the machine is kept awake with `caffeinate`. `add` and `check` make the task worktree and fetch the branch too (a clean local branch behind origin is fast-forwarded there). At the start of each task `git fetch origin <branch>` runs: a local branch behind origin with a clean worktree is fast-forwarded (`merge --ff-only`), a diverged one is refused with both SHAs, and a failed fetch (no network, no origin) is one line in the output and the run goes on with the local branch. The raw session log is created `0600`. Push and PR stay forbidden, as in any force run.

**What the second machine needs.** macOS, `claude` and `node` on PATH (a login shell is not read, so check `PATH` of the shell that starts `run`), the repo cloned, the task folder (`<task_dir>/<TICKET>/` with STAGES.md and the confirmed Force block) and the task branch pushed to origin. Before the night:

- the task worktree (`<repo>-<ticket>`, made by `add`) has what a fresh checkout lacks: the dependencies installed and the `.env*` files in place. Nothing is installed or copied for you; `check` names, per task, `node_modules`, the `.env*` files of the main copy's root and the main copy's `.claude/pipeline.config.local.md` when the worktree lacks them;
- a repo whose `.claude/pipeline.config.md` is committed with a relative `task_path`: the hooks of a session in the worktree look for the task in the worktree's own folder and find nothing, so the commit and journal guards would be silent. `add` and `check` refuse such a task and print the fix: create `<worktree>/.claude/pipeline.config.local.md` with `- task_path: <the absolute task folder of the main copy>`;
- the login is done in the `stage-pipeline-chrome` persistent profile (an `--isolated` login dies with the session), the Figma desktop app is open with the file, and the dev server is up. Otherwise the checks that need them are deferred as `[live: user-side — …]` at the interview, not made at night;
- the machine stays on with the lid open (`caffeinate -i` stops idle sleep, not lid-close sleep) and the queue is started under `tmux` or `nohup` (closing a terminal sends SIGHUP to `run`).

Run `check` first: it fetches each task branch (`git fetch origin <branch>`) and says, for every queued task, whether the repo, the task folder, the interview, the branch on origin, the worktree and `claude` are in place.

**The 5-hour limit.** The session stops with `usage_limit_reached`. The window and its reset time decide, not the text: a five-hour window that resets within five hours (and a quarter hour) is a wait even when the text says the org's monthly spend limit (a team seat at its org's cap still gets its window back); if the text names the org's monthly spend limit but the seat stays blocked after the reset, the task ends `gave_up` after `--max-sessions` new sessions (`force-run.mjs` exits 7): raise the org's limit or wait for the month, then `add <repo> <TICKET>` again and `run`. The queue waits until the reset plus 5 minutes (`--margin-min`) and starts a NEW session of the same task in the same worktree (never `--resume`). Before the next task it also waits if the window is already at the threshold.

**The weekly limit, the spend limit and a limit of unknown window.** The spend limit is an organization spend limit whose reset is more than five hours (and a quarter hour) away, or a spend text with no window or no reset time. The queue stops at once and prints the reset time (for a limit with no known window or reset time, there is none to print). The task that hit the limit and every task not started stay queued; the next `run` goes on with a new session. A task that failed for another reason does not stop the queue.

**The morning.** The summary is printed to stdout and written to `force-queue-summary.md` in the plugin data directory (`~/.claude/plugins/data/stage-pipeline-<marketplace>/`, or `$CLAUDE_PLUGIN_DATA`). One line per task: outcome, commits of the run, open blockers, `log:` (the raw log of its last session) and `digest:` (the path to its `RUN-DIGEST.md` when this run wrote it; otherwise `not written` with the `run-digest.mjs` command that writes it); then the reason the queue stopped and the tasks not started. The summary is rewritten after each task, so a crash keeps what was done.

On the second machine the run's commits stay local, because force never pushes. Before you go on with the task on another machine, push the branch from the task worktree (`<repo>-<ticket>`) and copy the task folder (`<task_dir>/<TICKET>/`) back; otherwise the other machine starts from the old journal and its branch diverges.

What to do with a line of the summary:

| Outcome | What it means | What you do |
|---|---|---|
| `completed` | the stages are done, the Force block is closed | read `RUN-DIGEST.md` (blockers, "Awaiting user confirmation"), then `/task-wrapup`; on the second machine, push the branch and copy the task folder back first |
| `completed` with open blockers | the run finished what did not depend on them | answer each blocker: write `Lifted: <who> <date> — <answer>` on its line in the Force block, then run the task again (`/stage-force <TICKET>`, or `--interview-only` and `add` for the queue). The `## Status:` line has to say the run is open again (`force run <date> not completed`; the interview rewrites it with the new block), because a closed status line closes the run for the hooks |
| `weekly_limit`, `spend_limit`, `limit_unknown` | the account limit (`spend_limit`: an org spend limit whose reset is more than five hours (and a quarter hour) away), or a limit with no known window or reset time (`limit_unknown`: the queue stops, nothing says when to go on); the task is still queued | wait for the reset time in the summary (or raise the organization's limit; for `limit_unknown` read the text of the limit in the log), then `run` again — nothing to repair |
| `stopped` | the session ended with the Force block still open | read the end of the raw log in the task folder and `RUN-DIGEST.md`. An interrupted run (Ctrl-C, SIGTERM) leaves the task queued: just `run` again. Otherwise `add <repo> <TICKET>` again (a finished ticket is re-added in place of its old entry), then `run`. Both continue from the first stage that is not done, with the resume point of the state on disk in the prompt |
| `gave_up` | several new sessions in a row closed no stage | something blocks the task: read the log, fix the cause (a login, a missing file), then `add <repo> <TICKET>` again and `run` |
| `error` | a non-zero exit or an API error; the text is in the line | the line says why; fix it, then `add <repo> <TICKET>` again and `run`. A finished entry stays in `list` until it is re-added (`remove` takes only a task that was not started); you can also take the task by hand with `/stage-force` |
| `not_ready` | the Force block is missing, closed or has no `Confirmed:` line, or the branch is not there; also: the hooks cannot see the task in the worktree (add the `task_path` line to its local config), the status line says the run is closed (update it), the task branch is checked out in the main copy, or the branch has diverged from origin | check the block and the branch (`force-queue.mjs check`), re-interview with `/stage-force <TICKET> --interview-only` if needed, then `add` and `run` |
| `busy` | another run holds this task | wait for it or stop it, `run` again |

Exit codes of `run`: `0` every task completed · `1` some task did not · `2` refused to start (a second `run` on this machine, or nothing queued) · `3` a limit with no known window or reset time · `4` interrupted · `5` weekly limit · `6` spend limit. `force-run.mjs <repo> <TICKET>` runs one task without the queue (exit codes: `0` completed, `1` error, `2` not ready, `3` `limit_unknown` — with `--once`, `limit`: the 5-hour limit, no wait —, `4` stopped, `5` weekly limit, `6` spend limit, `7` gave up).

## 2d. The tracker and the balancer — several sessions on one machine

Several Claude Code sessions in several repos share one machine, and what runs out first is memory: three `yarn test`, two browsers and the dev servers put it into swap. The plugin does two things about it: **the balancer** decides when a heavy command or a browser may start, and **the tracker page** shows the machine and lets you reorder the tasks. Nothing here needs the page: the balancer works through a registry in `~/.claude/stage-pipeline/` and the file `priorities.json` in the plugin data directory; the page only edits that file.

**Start the page.** In any Claude Code session: **`/stage-pipeline:monitor`**. It reuses the page that already runs on this machine, or starts it apart from the session (it keeps running when the session or VS Code closes; its output goes to `<data dir>/monitor.log`), and opens it in the browser; `/stage-pipeline:monitor stop` stops it. The same from a terminal: `node <plugin>/scripts/monitor.mjs open [--port N] [--no-browser]` and `… stop`. A running page is found through `<data dir>/monitor-server.json` (its pid and start), so a second `open` never starts a second server on the same port. To run it in the foreground instead:

```
node <plugin>/scripts/monitor.mjs serve [--port N] [--new-token]
```

It prints `monitor: http://127.0.0.1:7317/?t=<token>`. The address is fixed: port 7317 (`--port` changes it) and a token kept in `<data dir>/monitor-token` (mode 0600), the same after a restart; `--new-token` makes a new one. When the fixed port is already taken at the start, the start fails and the token is replaced at once, so the program that holds the port does not learn the token that the next start will use; the token is changed only then, so on a shared machine run `serve --new-token` yourself. The server listens on 127.0.0.1 only, wants the token on every request, checks `Host` and, for a POST, `Origin`, and takes task keys only, never a PID. A foreground `serve` lives as long as its process. `node <plugin>/scripts/monitor.mjs` alone prints the same snapshot as a table (`--json` as JSON), and `node <plugin>/scripts/heavy-queue.mjs status` the balancer's state.

**What the page shows.**

- **Waiting for you** — the sessions that have stopped for your answer, oldest first, each with how long ago and an *Open* link for a session that can be opened (it opens the session's own VS Code window if that window is the one in focus). A question, a permission prompt or a dialog gets a yellow plate: the two oldest with two lines of text (the tooltip has more) and the answer options on one line, the next ones a line each; the chats whose turn ended are rows of one pale plate, each last reply in its tooltip. The state comes from the `session-wait` hook, which writes one small file per session into `<data dir>/sessions/` and never blocks.
- **Tasks and stages** — one strip per task of every repo of the machine registry, laid out like a flight-strip bay. A strip opens with its state — *Problem*, *Needs you* (a chat asks something; the strip sticks out of the line), *Paused*, *Your turn* (a chat's turn ended), *Queued* (a heavy command waits), *Running*, *Live* (a chat is open, nothing heavy), *Idle* — then its place, the ticket and repo, the stage N of M with the next item, what runs now, the chats (how many, then the one that waits, else the latest), the memory and CPU of its chats, and *Pause*; the column names are printed once above the strips. A click on the strip (or Enter on a focused one) unfolds it: the stage heading, the next item in full, the heavy commands with their usage and command line, and the open chats. A chat is one Claude Code session: its title as VS Code shows it (the one you gave it, else the generated one), when it last wrote, its subagents, CPU and memory, its last prompt and an *Open* link; the title comes from the tail of the session's transcript in `~/.claude/projects/`. A tab opened without a session id (a new chat, before the `session-wait` hook has seen it) is matched to the newest transcript of its folder that started after it and that no other chat holds; such a guessed chat gets no *Open* link. Drag a strip (or Alt+Up / Alt+Down on a focused strip) to change the order: the first strip is place 1. The **Active / All** switch (the page remembers it in the browser) shows by default only the tasks with a live Claude session, a heavy command or a pause; **All** adds every open task nobody works on now. The number on a strip is its place among all of them, the one the balancer reads; reordering under **Active** puts the shown tasks above the hidden ones. Which task a session is shown under: see «Which task a session is under» below.
- **Heavy load by kind** — for every session the CPU and the memory of its process tree split into `check` (everything under `run-check`), `browser` (DevTools Chrome), `dev-server` and `other`; the heavy commands that run or wait, each with its state (`running`, `waiting` with the reason, `throttled`, `paused`): on the strip as a mark per kind, in full in the unfolded strip and in the **Heavy commands** list on the right.
- **The machine** — in the top bar: available memory with the pressure, swap, and the load against the cores, each coloured when it is high. **Memory by owner** on the right: one bar of the whole memory (each task's chats, the other apps, the free rest), then a row per owner with its share of the used memory, the largest first; pointing at an owner lifts its strip.

**Which task a session is under.** The `claude` process of a VS Code window stays in the window's folder, so the tracker does not take the task from it. It reads the folders named in the session's transcript (the newest lines of its tail) and takes the newest folder that has a pipeline task. A folder comes from a line's `cwd` and from the session's own tool calls: a Bash command that starts with `cd <path> &&` (or `;`) or with `git -C <path>`, and the folder of the `file_path` of an Edit, Write, MultiEdit or Read call or the `notebook_path` of a NotebookEdit call, each with the time of its line; a relative path is taken from the line's `cwd`, `~` from the home folder, and nothing else of a command or a file's text counts (a heredoc, an `echo`, a `cd` that is not first). A call into another repo does not move the session: a tool folder counts only inside the repo of the line's `cwd` (the same common git dir: a linked worktree counts, whatever the layout of the main tree — a bare clone and `--separate-git-dir` included), or when that `cwd` is in no checkout. The calls of subagents lie in their own transcripts and are not read. So several sessions of one window, each in the worktree of its own task, are in their own lanes; a session that went back to the main tree for one command stays with its task. The last `run-check` of the session (`session-tasks.json`) is the second source: of the two the newer wins, a source without a task never covers one with a task. Without a transcript, an id or any folder with a task, the pair decides, then the process's folder. A session in a worktree with no pipeline task is in the lane of the repo. A new tab has its id from the `session-wait` hook state from its first prompt, so it is placed by its transcript from the first turn on. The snapshot, the pause of a task's browsers (new tabs without `--resume` included, once the session-wait hook state gave the tab its id; a guessed id does not place a session) and the `browser-admit` hook all use this one rule (`pickSessionTask` in `heavy-queue.mjs`). The label of a lane is the name of the key's root; a task whose directory lies outside the repo and that has no live session takes the key from `priorities.json` with the same task directory and ticket.

**What priority, background and pause do.**

- **Priority** (the order of the cards) decides only when resources are short. While memory suffices, nobody waits, however many sessions run. A new heavy command or browser is admitted when its expected memory (the recorded peak of the same command, 1.5 GB without a history; 0.8 GB for a browser) fits into the available memory minus a 1.5 GB reserve; if not, the waiting ones go in the order of their effective priority — the place, one place up per minute of waiting — and a wait ends after 5 minutes (4 for a browser). At least one heavy command always runs, so nothing stands still. Memory is also the one thing a running command is never stopped for.
- **`nice`** is set from the place (10 for place 1, one more for each next place, 19 at most; 19 for a task not on the list), in both resource modes. It only shares the CPU between running commands.
- **Background under load** (macOS): when the cores have been busy for 30 s, the commands of the lower half of the running tasks go into the background class (`taskpolicy -b`, the efficiency cores), and out of it when the load falls. A lone command is never throttled. On Linux only `nice` applies.
- **Pause** (a button on the card, or `node <plugin>/scripts/heavy-queue.mjs pause|resume <task key>`; the key is `<repo root>#<TICKET>`) stops a task by hand and nothing pauses by itself: its running heavy command and its browsers (the main process and the helpers) get SIGSTOP and are continued by the resume, its waiting commands wait for the resume, and a new browser too, but not longer than the 4-minute cap. macOS and Linux; Windows has no pause.

**Browser admission.** A DevTools MCP browser is the heaviest thing a checker starts, and every session starts its own. The `browser-admit` hook runs before every DevTools call of a session: if the session already has its browser (and its task is not on pause), it passes at once; otherwise the new browser goes through the same admission by memory (kind `browser`, expected memory = the peak recorded for this machine, 0.8 GB at first). The wait is capped at 4 minutes (240 s; the host's hook timeout forbids an uncapped one), and then the call goes through with the line `browser: waited <s> s for memory, starting anyway` (`browser: waited <s> s for the resume, starting anyway` for a paused task). A heavy check does not wait for an open browser: browsers hold memory, which the check's admission counts, but they are not a running heavy command. It does nothing in `normal` mode, except that a task on pause holds its new browser until the resume, but not longer than the 4-minute cap. An admitted browser is counted as running while the session holds it; its peak (sampled whenever the registry is read, the highest sample within this browser's life) is stored when it goes as the mean of the stored value and this peak, so one spike decays over the next browsers. `STAGE_PIPELINE_BROWSER_WAIT_S` overrides the 4-minute browser cap and `STAGE_PIPELINE_BALANCE_WAIT_CAP_S` the 5-minute cap of a heavy command.

**Modes.** `resources: low | normal` in `pipeline.config.local.md` (default: `low` at 16 GB of RAM and less, `normal` above). In `low` the admission by memory applies to heavy commands and browsers. In `normal` memory is not looked at, but the order still sets `nice` and the pause still works.

**The heavy-guard denial.** In `low` mode a test, build, type_check or lint command that the repo's config names, run bare in a Bash call, is refused with the ready `run-check` command (rule `git-guard/heavy-guard-bypass`): a command that bypasses `run-check` bypasses the balancer. `STAGE_PIPELINE_HEAVY_GUARD=off` in the environment turns the rule off; `resources: normal` never triggers it.

**What is not controlled.**

- Memory can be shared only by the admission (who starts when) and by the pause (a stopped process keeps its memory but takes no CPU). A running command is never killed or stopped by the machine's state.
- Dev servers are only shown, never started, stopped or throttled.
- The load on the API (the five-hour window of the Claude account) is not local: that is what `force-queue.mjs` waits for.
- Priority cannot go above normal without sudo: "main task" means "the others are lower", through `nice` and the background class.
- A browser or a command that was already running before the plugin update is not in the registry until it starts again.

## 3. Task finale

- A full `pro-review` over the whole branch (an agent in whole-branch mode on `review_model`, the base is `origin/<main_branch>`, that is, the PR target: if PRs go into `dev`, the config has `main_branch: dev`). Since 0.24.0 the report records the reviewed commit (`head:`), and a force run's fix round after the final checks is re-reviewed by a **delta review** (`pro-review --delta checks/<full report>`, the change since that commit, on `review_model`) with a fresh `task-converge`; a critical or major from it gets one more round and a second delta, one from the second delta is a blocker. The hook counts a delta only on top of a full report whose commit is an ancestor of HEAD and up to 400 changed lines since it; over that, a full whole-branch review is the new anchor. A report written before 0.24.0 has no `head:` line, so it stays reviewable only in full.
- `floor-guard --base origin/<main_branch>` — the quality floor over the whole branch: silenced checkers, weakened tests, stubs.
- security-review, metrics-guard (if the config has `bundle_size`), ds-parity, dead-code, i18n-sweep, deps-audit (per STAGES "Final checks").
- **`/task-converge`** — the code on HEAD against the intent of the task. All other checkers look into the diff and answer "is what was done done right"; converge answers "was everything promised done, and was nothing extra done". A criterion that no stage took on does not appear in the diff — its absence is invisible by definition. Findings → a "Catch-up" block in STAGES.md (append-only, rewriting nothing) → a repeated run until it converges.
- **`/task-wrapup`** → `PR.md` — a PR/MR description from the task journal, written by the human-text rules and checked by `human-text-check`: what and why, how to verify, what the reviewer should look at, blind spots, open questions. Manual only, when the description is needed: neither force nor the final checks call it. Pushing and creating a PR are also manual.
- A legacy removal / cleanup is a separate final stage.

**Models.** The orchestrator (the `/stage-*` skills) runs on the model of your session — the plugin does not set it; the recommended one is Opus (`/model`). The agents use the `model:` field in the frontmatter. Five of those choices were **measured**, ten were **chosen by role**:

| Model | Agents | How it was chosen |
|---|---|---|
| `haiku` | `deps-audit` | **measured**: on the eval case not worse than Sonnet at a 2.5 times lower price (CHANGELOG 0.9.0) |
| `sonnet` | `docs-lookup`, `i18n-sweep` | **measured** against Haiku in the same run (CHANGELOG 0.9.0): Haiku looked better on one branch of `docs-lookup`, but with a key it did not hold, and `i18n-sweep` on Haiku did not quote the string it found |
| `sonnet` | `security-review`, `ds-parity` | **measured** against Opus, one run on one case each (CHANGELOG 0.25.0): the same findings and no false ones, about 1.6–1.9 times faster and 2.5–2.7 times cheaper. Before 0.25.0 both ran as general-purpose agents on the session's model; agent-guard now rejects that |
| `sonnet` | `stage-implement`, `pro-review`, `task-converge`, `figma-compare`, `figma-spec`, `proto-compare`, `proto-spec`, `devtools-verify`, `api-verify`, `contract-compare`, `dead-code`, `human-text-check` | **by role**, not measured against another model: judgment and accuracy, a false green from a checker is worse than a red one, and noise is refuted by the expensive orchestrator |

The 0.9.0 measurement ran on Sonnet 4.6, before the `sonnet` alias moved to Sonnet 5, and was not repeated. The first exception to the table is the whole-branch pro-review and the fresh checker run in the fix-loop: they go on `review_model` from the config (`opus` by default) through the `model` parameter: the last check by the strongest model, and in force also not the one that wrote the code (`/stage-check`, Step 3.3). For whole-branch the agent-guard hook enforces this: in live runs 5 of 14 such reviews went to sonnet because the parameter was forgotten. The second exception is `security-review` when the config sets `security_model` (optional, no default): agent-guard then holds that agent to the named model through the same `model` parameter and denies a call that differs (`agent-guard/security-model`); with no key it stays on sonnet as in the table. The agent names in agent-guard are compared the way the host reads them (case, `_`, dashes and white space ignored), so `Security_Review` is held to the same rules.

The `sonnet` alias resolves differently depending on the Claude Code version: in 2.1.193 to Sonnet 4.6, in 2.1.276 already to Sonnet 5. The real model is shown by `modelUsage` in the summary of an eval run. **Drift is checked:** `evals/models.json` holds the last resolved model per agent (the model the agent itself ran on, not the haiku parent of the eval harness), and an `eval.mjs` run whose agent resolves to another model prints `model drift: agent <a> resolved to <got>, evals/models.json has <expected>`. The file is never rewritten by a run on its own: look at the pass rate and the cost, then accept with `--accept-models` (or regenerate it from the ledger with `--seed-models`). If you need a specific model, put an explicit id into the frontmatter (`claude-sonnet-5`). Before changing an agent's model: `node scripts/eval.mjs --runs 3 --model <agent>=<model> <the agent's cases>`.

**Effort.** One agent sets `effort:` in its frontmatter: `docs-lookup` has `effort: medium`. It was **measured** (CHANGELOG 0.23.0, «Effort measurement», N=3 runs per case, Claude Code 2.1.314): the same pass rate as no line (3/6, the case `docs-lookup-not-installed` fails at every level), about 10 % cheaper ($0.074 against $0.083 per run) and about 10 s faster (21 s against 31 s); `medium` over `low` as the smaller cut for the same gain. `pro-review` and `human-text-check` were measured too and keep no line: `low` and `medium` each lost one run (`pro-review` 17/18 and 16/18 against 18/18, `human-text-check` 11/12 at both against 12/12). The other agents were **not measured** and carry no `effort:`; for them it is left to the session. N=3 is small, so treat a measured line as a default to re-check, not a proof. `node scripts/eval.mjs --effort <agent>=<low|medium|high|xhigh|max|none> <cases>` runs the cases against a copy of the plugin with that line set (`none` removes it); the ledger row is labelled `effort:<agent>=<level>`. `effort:` is set on an agent only where the pass rate and the cost do not get worse.

**Three narrow checkers instead of one big one.** `pro-review` answers for correctness, security and conventions. `dead-code`, `i18n-sweep` and `deps-audit` each answer for their own class of junk, with their own confirmation procedure, and run **by a trigger**: something was deleted → dead-code; user text appeared → i18n-sweep; the manifest was touched → deps-audit. No sign — `[skip: no trigger]`, no extra subagent is spent.

**Replacing checkers per repository.** The design source is not Figma but a file one (a repository of HTML prototypes from AI designers): `pipeline.config.md` declares `figma-spec → proto-spec`, `figma-compare → proto-compare` in the "Checker overrides" section — the kickoff/check orchestrators read the config and take the named agents. The rest of the loop is unchanged; such a repository does not need the Figma MCP.

## Repo rules and `/promote` — repeats become rules

**`## Repo rules`** in `pipeline.config.md` (no table — nothing changes). One row per rule: `| id | pattern | files | message | evidence |`. The pattern is a JS regular expression over one added line (write an alternation as `\|` in a cell), `files` are globs (`**/*.vue`, `!**/*.test.*`, `*` for every file) written in one code span, `` `src/**/*.vue, !**/*.test.*` `` (several spans, one per glob, are read the same; a glob is repo-relative, so a directory is written `dir/**`, not `dir/` or `./dir`, and a glob with a leading `./`, a trailing `/` or a stray backtick is a config problem naming the row), the message says what to do instead, evidence says where the rule came from. floor-guard applies the rows to **added lines only**, prints `[repo:<id>]` with the row's message, and the force-commit hook denies the commit like any other floor violation. `floor-ok: <reason>` on the line (or the one above) waives it, and the run digest lists every waived rule under "Repo rules waived by floor-ok". A row that cannot be used (a pattern that does not compile or matches an empty line, a bad glob, a duplicate id, a pattern that can backtrack without end such as `(\w+\s?)+`) is printed once as a config problem and the commit is reported as unchecked, never passed silently. A row whose pattern throws when floor-guard checks it (e.g. a stack overflow) is a named config problem too, with the cause of the error, and the other rows keep running; a table that cannot be parsed at all is one config problem and floor-guard exits 2 when there are no violations. pro-review rubric A does not re-report a convention that a row enforces.

**`/promote`** (manual only) finds what the checkers raise again and again and stops it for good. Inputs: `retro.mjs --findings`, the review corpus when given, merged PR/MR comments if you export them (it never calls `gh` or `glab`), repeated dismissals per checker. For each class with two or more hits it picks the highest level that works: an architecture or delete stage, types, a lint rule, a Repo rules row, a CLAUDE.md line. It then **proves** the candidate with `scripts/promote-proof.mjs` and shows the output with the revs and counts: fires on at least two real pre-fix versions, quiet on HEAD. A rule that does not prove is not offered; a CLAUDE.md line is offered marked unproven. **Nothing in the project changes without an explicit yes per rule.** Lint config, CLAUDE.md and types are offered only as items of the task (a line under "Not included in the plan"); a Repo rules row is written to `pipeline.config.md` only after that yes, and the file is shared, so it goes in a separate commit that you make. The reverse direction: repeated false positives become entries of `skills/<checker>/references/false-positives.md` (skip when / do not skip when / example / source), with a "never skipped" list at the top of each file; `kit-override-scan.mjs` applies its patterns itself and lists every skipped hit in the report with the pattern id (`--reference <file>` names the stage's reference file for the `reference-line` pattern).

**`team_review`** (opt-in, in the config's `## Final checks` section): `- team_review: <skill>` makes the force close require the repo-local review skill's report `checks/<skill>-branch.md` fresh, or the blocker marker `[final: <skill> — not run|stale]`. No line — no extra report.

## human-text and feature-doc — outside the loop

Two manual skills for text that people read. Neither is called by the pipeline's stages or hooks.

- **`/stage-pipeline:human-text <to whom> <about what>`** — text about a project for the team, a manager, a newcomer or a client. It also installs on its own, without the pipeline: `claude plugin marketplace add maggi08/claude-pipeline`, then `claude plugin install human-text@magzhan` (the command is then `/human-text:human-text`).
- **`/stage-pipeline:feature-doc [feature]`** — a doc on a finished feature in `docs/features/`. If a separate `feature-docs` plugin is installed, this does the same job; both are manual, pick one per repository.

**For whoever edits the plugin.** `skills/human-text/` and `agents/human-text-check.md` are a vendored copy; the source of truth is the repo `maggi08/human-text`. `plugins/stage-pipeline/human-text.lock.json` pins the source commit and the sha256 of each copied file. Change the rules in the human-text repo, then run `node scripts/sync-human-text.mjs` (from the marketplace repo; `../human-text` by default, or a path or a git ref as an argument) and commit the copy together with the lock. `node scripts/validate.mjs` fails on a hand edit of the copy.

## Files (in the repository — `<repo>/.claude/`)

- `pipeline.config.md` — the project profile (read by all skills).
- `tasks/<TICKET>/` — `STAGES.md` (the journal: what/when/why/outcome), `specs/`, `checks/`, `DESIGN-QUESTIONS.md`.
- `memory/` — project memory (decisions/pitfalls of this repository).

Keep project review checklists in `CLAUDE.md` or in `pipeline.config.md → Conventions`, NOT in the plugin skills: the plugin is read in all repositories, and someone else's rubric produces false Majors.

## Context hygiene (the main lever of spending)

The full version with measurements — [references/context-hygiene.md](references/context-hygiene.md).

- Checks go through subagents (heavy Figma dumps/snapshots/diffs do not settle in the main context).
- After closing a stage — `/clear` (typed by the user); chrome-devtools and Figma through subagents, not from the main context; in force the stages go through subagents and there is nothing to clear.
- `evaluate_script` (numbers) instead of screenshots for measurements; `take_snapshot` only for the uid.
- Text fidelity: placeholder vs dynamic, exact characters (—/₸/«»/nbsp), i18n against the resolved locale.
- Read big trackers (STAGES.md) selectively (offset/grep).
