# DS Parity — дубли между приложением и дизайн-системой

Цель: убрать из PR два класса дублирования — (а) hand-rolled UI там, где в ките уже есть компонент; (б) локальные компоненты, которые по смыслу общие и должны жить в ките, чтобы другие приложения их не переписывали.

Мотивация (реальный замер, chekin-guestapp 2026-07-30): у разработчика на редизайне ~90% времени уходит не на написание, а на ревью и повторные запросы на фиксы — флоу пишется за час, потом 4 часа проверок и рефакторинга, и львиная доля правок именно про дубли с UI-китом. Этот проход дешевле, чем ловить их глазами по кругу.

> **Project config.** Репо кита, префикс компонентов и раскладку кода бери из `<repo>/.claude/pipeline.config.md` (`ui_lib`, `components`, `page_components`; нет файла — `/pipeline-init`).

## Обязательное предусловие: свежесть кита

Вывод «в ките такого нет» без свежих рефов — недостоверен. Перед поиском:
- `git -C <ui-repo> fetch --all --prune`;
- искать не только точное имя, но и синонимы (`Language*`, `Locale*`, `*Switcher`, `Country*`, бренд-префиксы);
- сверить версию установленного пакета с версией на ветке разработки кита: **компонент может быть в ветке и не быть в npm** (chekin-ui: `origin/next` beta.60 против реестра beta.53).
Проверено дважды: оба раза «компонента нет» оказалось следствием рефов недельной давности.

## Процедура

Гонять **параллельными субагентами** (Explore), не инлайном: три независимых прохода дешевле по контексту и не заражают друг друга выводами.

1. **Парити по дифу PR** — только изменённые файлы. Что hand-rolled в этом PR и чем заменяется.
2. **Парити по дереву** — breadth-свип всего приложения по функциональным категориям (модалки/шиты, дропдауны, селекты, табы, лоадеры/скелетоны, прогресс, бейджи/статусы, карточки, тултипы, таблицы, инпуты/OTP/даты, empty-state, тосты, копирование в буфер, флаги/языки).
3. **Кандидаты на промоушен** — локальные компоненты без доменных импортов (нет чтения контекстов резервации/гостя, нет react-query, нет фичевых i18n-ключей), у которых есть смысл для других приложений.

Каждому агенту в промпт: путь к репо кита + как читать его исходники (`git show <ref>:<path>`), путь к установленным типам (`node_modules/<ui-lib>/dist/index.d.ts`), скоуп поиска и требование **читать реальные сигнатуры пропсов, а не угадывать по имени**.

## Правила вывода (иначе отчёт бесполезен)

- **Матчить по функции, а не по имени.** «Наш `Sheet` ↔ китовый `ResponsiveSheet`» — находка; «наш `Card` ↔ китовый `Card`» без проверки пропсов — угадывание.
- **Называть, что теряет hand-rolled версия**, конкретно: управление фокусом, клавиатура, портал (popover без портала режется любым `overflow:hidden`-предком), ARIA-связки, токены/темизация, dark-вариант. Это превращает находку из вкусовщины в дефект.
- **Локальная обёртка над китовым компонентом — НЕ дубль.** Не флагать. Дубль — это своя реализация той же механики.
- **Цена миграции** у каждой находки: drop-in / нужны пропсы / нужна правка в ките.
- **Промоушен только с конкретной сигнатурой** будущего DS-компонента и списком того, что надо распараметризовать (контексты, i18n-ключи, сторы).
- **Отрицательный результат — тоже результат**: перечислить категории, где дублей нет, и компоненты, которые осознанно остаются локальными (фичевые). Без этого остальному отчёту не верят.
- Ранжировать по «выигрыш × низкий риск», не по алфавиту. Больше call-sites — сильнее аргумент.

## Выход

Компактная таблица в чат (и в `<task_dir>/<TICKET>/checks/ds-parity.md`, если есть task-дир):

```markdown
| # | Наше | DS-аналог | Что теряем | Миграция | Уверенность |
|---|------|-----------|------------|----------|-------------|
```
Плюс раздел «Кандидаты в кит» (наше → предлагаемая DS-сигнатура → что распараметризовать → call-sites) и раздел «Осознанно локальное».

Дальше — как обычно: подтверждённые находки чинит оркестратор, спорные и требующие правок в ките уходят в трекер вопросов к DS (в chekin-guestapp — `DESIGN-QUESTIONS.md`).
