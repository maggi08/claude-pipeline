# Прецеденты правил /stage-check

Откуда взялось каждое правило. Для исполнения этапа файл не нужен — правила в `SKILL.md` самодостаточны; он нужен, когда правило хочется ослабить или переписать.

| Правило (Шаг) | Прецедент |
|---|---|
| Инвентарь прошлых этапов в промпт pro-review (Шаг 1) | Ручное ревью PR принесло 10 замечаний, 6 из них — дубли, растянутые по этапам: справочные данные, legal-ссылки, `formatTime`, обёртка шага в 4 копиях, порядок шагов в 3 местах, провайдер поверх существующего хука. Каждый этап закрывался с зелёным pro-review. |
| Продуктово-видимое — отдельной строкой в «Ожидают подтверждения» (Шаг 4.1) | «ПОДТВЕРДИТЬ на user-review» утонуло в прозе журнала и всплыло только на QA. |
| Журнал обязателен (Шаг 4.1) | Из журнала собирается командный ONBOARDING.md; без журнала объяснить подход задачи нечем. |
| Архивация скриптом (Шаг 4.2) | Замер по 30 живым задачам в четырёх репо: 17 STAGES.md больше 40 KB, до 153 KB (≈40k токенов на каждое чтение); при ручном правиле архив был у пяти задач. Журнальные записи по ~2 KB против правила «3–6 строк». |
| Единое имя отчёта `<checker>-<stage>.md` (Шаг 4.3) | В живых задачах четыре схемы: `pro-review-2.md`, `stage2-pro-review.md`, `stage-2-pro-review.md`, `stage-2/pro-review.md`. |
| Строка `metrics:` в журнале (Шаг 4.1) | Ретро 0.2.0–0.8.0 опирались на числа из памяти; ни одна из 182 закрытых этапных записей не содержала машиночитаемых метрик. |
| Коммит в обычном режиме — только текст (Шаг 4.4) | Замер по одной задаче: из 40 отклонённых вызовов больше половины — `git add` и `gh pr comment`. С 0.9.0 правило держит ещё и хук `git-guard`. |
| Коммит сразу после fix-loop (Шаг 4.4) | Ребейз уничтожил применённые, но не закоммиченные cleanup-правки; восстанавливали по памяти. |
| `/clear` после этапа — дефолт (Шаг 4.5) | Замер за четыре дня: 177M cache-read токенов, 98M из них — один день-марафон; средний контекст запроса 234k. |
