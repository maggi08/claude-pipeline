# Environment preflight — before running the checkers

Read from `/stage-check`, Step 0, and `/root-cause`, Step 0. A green run on a broken environment is worse than a red one: it closes the stage with a lie. Five checks, each of which really ate cycles:

1. **The installed tree ↔ the manifest.** `ls -la node_modules/<ui-lib>` + the version from `package.json`. A symlink/`link:`/`portal:` to a neighboring repo with a pinned registry version = all local checks run on code that the pinned version does not have; the branch is red in CI. The reverse case — the manifest asks for `link:` but a registry tarball is installed: the neighboring repo's edits are simply not visible, and "the code does not work" looks like an implementation bug.
2. **Freshness of the built `dist` of workspace packages.** A package that resolves through built output (not through src) goes stale after a rebase/branch switch and gives false `Property does not exist` — rebuild before, do not debug after.
3. **The bundler cache after a linked package is rebuilt.** Vite and the like keep a pre-bundle: the neighboring repo's edits are not visible until you delete the cache and restart the dev server. The symptom is deceptive — it looks like "the code did not apply".
4. **Duplicate runtime dependencies from the linked repo.** A second copy of the framework or the i18n library (React, Vue, i18next — whatever the project has) from the neighbor's `node_modules` fails tests in files unrelated to the diff. Before fixing "your own" failures — run the same tests on a clean tree (`git stash`): the same set of failures means it is the environment, not the diff. Such a run is mandatory BEFORE you record failures in the stage report.
5. **Liveness of the test fixture.** The token/link/booking for a live check dies silently in the middle of a task. Check before running devtools-verify, otherwise the checker returns a FAIL about a design it did not see.
