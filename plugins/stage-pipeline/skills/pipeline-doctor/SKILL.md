# Pipeline Doctor — проверка окружения разработчика

Цель: за один прогон убедиться, что на этой машине работает всё, что нужно
пайплайну, и подсказать фикс для того, что не работает. Сам пайплайн приезжает
плагином `stage-pipeline` — доктор проверяет только окружение вокруг него.

## Чек-лист (по порядку)

1. **MCP-серверы.** Канонические имена задаёт `.mcp.json` плагина: `figma` и
   `chrome-devtools`. Проверь через ToolSearch доступность
   `mcp__figma__get_metadata` и `mcp__chrome-devtools__list_pages`.
   - Figma-тулов нет → (а) project-серверы не одобрены — подсказать `/mcp` →
     approve; (б) Figma desktop не запущена или выключен MCP-сервер
     (Figma → Preferences → **Enable Dev Mode MCP Server**). Проверка порта:
     `curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:3845/mcp` —
     любой HTTP-код = сервер жив, connection refused = выключен.
   - chrome-devtools нет → нужен Node ≥ 18 (`npx -v`); сервер поднимается сам
     через npx при первом вызове, Chrome должен быть установлен.
   - Если у разработчика есть user-scope сервер на тот же эндпоинт, но под
     ДРУГИМ именем — это дубль: скиллы и пермишены завязаны на канонические
     имена, дубль стоит удалить (`claude mcp remove <имя> -s user`).

2. **Соседние репо.** Сверь пути из `pipeline.config.md → Platforms /
   related repos` — каждый должен существовать на диске.
   Не совпадают с реальной раскладкой → спроси фактические пути и создай
   `.claude/pipeline.config.local.md` с секцией `## Platforms / related repos`
   (поля local перекрывают базовый конфиг; файл gitignored).

3. **Dev-сервер.** `Dev server → url` из конфига (+ local-оверрайд). Если у
   разработчика другой порт/протокол — тоже в `pipeline.config.local.md`.

4. **Baseline (опционально, ~минута).** `type_check` из конфига → сравнить
   число ошибок с baseline. Разъехался — предложить обновить baseline в
   базовом конфиге (общий файл — отдельным коммитом, не молча). Два подвоха:
   - **Монорепо-маскировка**: общий скрипт с топологическим порядком
     (`workspaces foreach -t`, turbo/nx) молча пропускает зависимые
     workspace'ы при падении их зависимости; подозрительно быстрый прогон =
     пропуск — сверяй прямым `tsc -p <app>` главного приложения.
   - **Свежесть локальных пакетов**: baseline-ошибки «модуль не экспортирует X»
     про `file:`-tarball/workspace ui-lib = сначала переустановить пакет,
     потом мерить baseline (устаревший tgz маскируется под легаси-долг).
   - **Установленное дерево ≠ манифест** — самый дорогой из подвохов, потому
     что он делает проверки зелёными неправдой. `ls -la node_modules/<ui-lib>`
     и сравни с версией в `package.json`: симлинк (`link:`/`portal:`) на
     соседний репо при запиненной реестровой версии значит, что всё локально
     проверяется по коду, которого в запиненной версии нет, — красным станет
     только CI. Обратный случай тоже бывает: манифест просит `link:`, а стоит
     реестровый tarball, и правки соседнего репо просто не видны.
     Расхождение → сказать, какой режим нужен разработчику, и привести дерево
     к манифесту (`install`), а не подгонять манифест под дерево.
     Отдельно: `link:` резолвится ОТ ВОРКСПЕЙСА, не от корня монорепо —
     из `apps/<app>` до соседнего репо это `../../../<repo>`; неверная
     глубина даёт битый симлинк и падение на этапе загрузки конфига
     (PostCSS/бандлер: «Cannot find package»), а не понятную ошибку.
   - **Дубли рантайм-зависимостей от линкованного соседа**: вторая копия
     React/i18next из его `node_modules` роняет тесты в файлах, к работе не
     относящихся. Замерь состав падений на чистом дереве и запиши как
     известный шум окружения, иначе каждая сессия чинит его заново.

5. **Разрешения: имена скиллов сменились вместе с переездом в плагин.**
   Скилл, приехавший плагином, вызывается как `stage-pipeline:<имя>`, а не
   `<имя>`. Значит записи вида `Skill(pro-review)` / `Skill(pro-review:*)`,
   накопленные пока скиллы лежали в личном user-скоупе, больше НИЧЕГО не
   разрешают — и каждый чекер снова спрашивает подтверждение на каждом этапе.
   Проверь `.claude/settings.local.json`: есть ли `Skill(stage-pipeline:*)`-форма
   для всех скиллов, которые гоняет пайплайн. Нет → добавить (старые записи
   можно оставить, они безвредны). Заодно в `additionalDirectories` должен
   лежать путь к репо плагина — иначе чтение и правка самих скиллов
   (ретро, донастройка) спрашивает разрешение на каждый файл.
   Симптом, по которому это узнаётся: «раньше не спрашивал, теперь спрашивает
   на том же действии» — почти всегда переименование субъекта правила, а не
   ужесточение политики.

6. **Итог.** Компактная таблица: пункт | статус (OK/FAIL/SKIP) | что сделать.
   Всё OK → окружение готово, дальше по `${CLAUDE_PLUGIN_ROOT}/README.md`.
